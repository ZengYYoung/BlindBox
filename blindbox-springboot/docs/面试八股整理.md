## 一、计算机网络

### 1.1 TCP 三次握手

```
Client                          Server
  |                                |
  |── SYN = 1, seq = x ──────────→|  SYN_SENT
  |                                |
  |←─ SYN = 1, ACK = 1, seq = y,  |  SYN_RCVD
  |    ack = x + 1 ───────────────|
  |                                |
  |── ACK = 1, seq = x + 1,      →|  ESTABLISHED
  |    ack = y + 1 ───────────────|
  |                                |
```

**为什么是三次，不是两次？**

两次握手无法防止**历史连接请求**到达服务端。如果客户端第一个 SYN 在网络中滞留，客户端超时重发 SYN 并成功建立连接并关闭后，滞留的 SYN 才到达服务端，服务端会误以为是个新连接并分配资源。三次握手可以让客户端发送 RST 拒绝历史连接。

**为什么不是四次？**

三次已经能确认双方收发能力正常，再多次只是冗余。

### 1.2 TCP 四次挥手

```
Client                          Server
  |                                |
  |── FIN = 1, seq = u ──────────→|  FIN_WAIT_1
  |                                |
  |←─ ACK = 1, seq = v,          |  CLOSE_WAIT
  |    ack = u + 1 ───────────────|
  |                                |
  |←─ FIN = 1, ACK = 1,          |  LAST_ACK
  |    seq = w, ack = u + 1 ─────|
  |                                |
  |── ACK = 1, seq = u + 1,      →|  TIME_WAIT (2MSL)
  |    ack = w + 1 ───────────────|
  |                                |
```

**关键点**：
- 服务端收到 FIN 后先回 ACK（半关闭），等数据发送完再发 FIN
- 客户端收到 FIN 后进入 TIME_WAIT，持续 **2MSL** 后关闭
- **TIME_WAIT 的作用**：防止最后一个 ACK 丢失导致服务端超时重发 FIN；让滞留的报文段在网络中过期

### 1.3 TCP 与 UDP 区别

| | TCP | UDP |
|--|-----|-----|
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠（确认重传、排序） | 不可靠（尽最大努力交付） |
| 速度 | 慢（头部 20B） | 快（头部 8B） |
| 拥塞控制 | 有（慢启动、拥塞避免、快重传、快恢复） | 无 |
| 应用 | HTTP/HTTPS/FTP/SSH | DNS/视频直播/游戏 |

### 1.4 TCP 拥塞控制（四个算法）

```
拥塞窗口 cwnd 变化：
① 慢启动：cwnd 指数增长（1→2→4→8...），直到 ssthresh
② 拥塞避免：cwnd 线性增长（+1），直到丢包
③ 快重传：收到 3 个冗余 ACK 立即重传，不等超时
④ 快恢复：cwnd = ssthresh + 3，进入拥塞避免
```

**慢启动门限 ssthresh**：丢包时，ssthresh = cwnd / 2，cwnd 重置为 1（TCP Tahoe）或 ssthresh + 3（TCP Reno）。

### 1.5 HTTP 与 HTTPS

| | HTTP | HTTPS |

  |                                                |

### 1.7 浏览器输入 URL 到页面展示全过程

```

⑤ 浏览器解析 HTML，构建 DOM 树
⑥ 加载 CSS、JS、图片等资源（重复 ②-④）
⑦ 渲染页面
```

## 二、操作系统

### 2.1 进程 vs 线程

| | 进程 | 线程 |
|--|------|------|
| 资源拥有 | 独立的地址空间、文件描述符、堆 | 共享进程资源，独享栈和寄存器 |
| 切换开销 | 大（需切换页表、刷新 TLB） | 小（共享地址空间） |
| 通信方式 | IPC（管道、消息队列、共享内存、信号量、Socket） | 直接读写共享变量 |
| 独立性 | 一个进程崩溃不影响其他 | 一个线程崩溃导致整个进程退出 |

**进程间通信方式**：
1. **管道**：父子进程间，半双工
2. **消息队列**：内核维护的消息链表
3. **共享内存**：最快的 IPC 方式，需要信号量同步
4. **信号量**：用于进程/线程同步
5. **Socket**：跨网络通信
6. **信号**：异步通知（如 SIGKILL、SIGINT）

### 2.2 死锁

**四个必要条件**（缺一不可）：
1. **互斥**：资源一次只能被一个进程使用
2. **持有并等待**：进程持有资源的同时等待其他资源
3. **不可剥夺**：资源只能由持有者主动释放
4. **循环等待**：进程间形成循环等待链

**预防**：破坏任意一个条件
- 破坏"持有并等待"：一次性申请所有资源
- 破坏"不可剥夺"：申请不到就释放已持有的
- 破坏"循环等待"：资源按序分配（按编号顺序申请）

**银行家算法**：避免死锁的经典算法，分配前检查系统是否处于安全状态。

### 2.3 进程调度算法

| 算法 | 描述 | 特点 |
|------|------|------|
| FCFS | 先来先服务 | 公平但平均等待时间长 |
| SJF | 短作业优先 | 平均等待时间最短，但长作业可能饿死 |
| 时间片轮转 | 每个进程运行一个时间片 | 响应快，适合分时系统 |
| 优先级调度 | 高优先级先执行 | 低优先级可能饿死（可配合老化） |
| 多级反馈队列 | 多级队列，不同时间片大小 | Unix 使用，兼顾响应和吞吐 |

### 2.4 虚拟内存与分页

**虚拟内存的目的**：
- 隔离进程地址空间，一个进程不能访问另一个的内存
- 让程序可以使用比物理内存更大的地址空间
- 简化内存管理（每个进程看到连续的虚拟地址）

**分页**：
- 虚拟地址 → 页号 + 偏移量
- 页号 → 页表 → 物理页框号 → 物理地址
- **TLB（快表）**：缓存最近使用的页表项，加速地址转换

**页面置换算法**：
| 算法 | 描述 | 优缺点 |
|------|------|--------|
| FIFO | 淘汰最先进入的页 | 实现简单，可能把常用页换出 |
| LRU | 淘汰最久未使用的页 | 性能好，实现成本高 |
| Clock（NRU） | 近似 LRU，用访问位 | 折中方案，Linux 实际使用 |

### 2.5 用户态 vs 内核态

- **用户态**：应用程序运行的模式，权限受限，不能直接访问硬件
- **内核态**：操作系统运行的模式，可执行特权指令，访问所有资源
- **切换**：系统调用（如 read、write）→ 陷入内核 → 执行 → 返回用户态
- **开销**：切换需要保存/恢复上下文、检查权限，比函数调用贵

### 2.6 Linux 常用命令

| 命令 | 用途 |
|------|------|
| `top` / `htop` | 查看系统进程、CPU、内存使用 |
| `ps aux` | 查看所有进程 |
| `netstat -tlnp` | 查看端口占用和监听 |
| `grep` | 文本搜索 |
| `awk` / `sed` | 文本处理 |
| `find` | 文件查找 |
| `chmod` / `chown` | 权限管理 |
| `df -h` / `du -sh` | 磁盘使用情况 |
| `curl` | HTTP 请求调试 |
| `tcpdump` | 网络抓包 |

## 三、Java 基础

### 3.1 HashMap

**数据结构**：数组 + 链表 + 红黑树（JDK 1.8+）

**核心参数**：
- 默认容量：16
- 负载因子：0.75
- 树化阈值：8（链表长度 ≥ 8 且数组长度 ≥ 64 时转为红黑树）
- 退化为链表阈值：6

**put 流程**：
```
① 计算 key.hashCode() → 二次扰动 (h ^ (h >>> 16))
② (n - 1) & hash 计算数组下标
③ 空 → 直接插入
④ 非空 → 链表遍历/红黑树查找
   ├─ key 已存在 → 覆盖 value
   └─ key 不存在 → 尾插法新增（JDK 1.8）
⑤ 元素数 > threshold（容量 × 负载因子）→ resize 扩容为 2 倍
```

**扩容为什么是 2 的幂次**：
`(n - 1) & hash` 等价于 `hash % n`，但位运算更快。扩容后元素要么在原位置，要么在原位置 + oldCap，不需要重新计算 hash。

**线程安全**：
- HashMap 非线程安全（多线程 put 可能导致死循环（JDK 1.7 头插法）或数据丢失）
- 替代方案：ConcurrentHashMap / HashTable / Collections.synchronizedMap

### 3.2 ConcurrentHashMap

**JDK 1.7**：分段锁（Segment 继承 ReentrantLock），默认 16 个 Segment，put 只锁一个 Segment
**JDK 1.8+**：synchronized + CAS，锁住的是数组的**头节点**

```
put 流程（JDK 1.8）：
① 计算 hash
② 空数组 → CAS 初始化
③ 数组对应位置为空 → CAS 直接插入
④ 非空 → synchronized(头节点) → 链表/红黑树插入
⑤ 元素数 > 阈值 → 扩容
```

**效率为什么比 HashTable 高**：
HashTable 锁整个方法（`synchronized`），ConcurrentHashMap 只锁节点，并发度随数组长度增加。

### 3.3 ArrayList vs LinkedList

| | ArrayList | LinkedList |
|--|-----------|------------|
| 底层 | 动态数组 | 双向链表 |
| 随机访问 | O(1) | O(n) |
| 插入/删除（中间） | O(n) | O(1)（需先找到位置） |
| 内存占用 | 紧凑 | 每个节点存前后指针，占更多内存 |
| 扩容 | 1.5 倍扩容，复制数组 | 不需要 |

**使用场景**：频繁随机访问用 ArrayList，频繁头部插入/删除用 LinkedList。

### 3.4 线程池

**七个核心参数**：

```java
new ThreadPoolExecutor(
    corePoolSize,      // 核心线程数
    maximumPoolSize,   // 最大线程数
    keepAliveTime,     // 空闲线程存活时间
    unit,              // 时间单位
    workQueue,         // 阻塞队列
    threadFactory,     // 线程工厂
    handler            // 拒绝策略
);
```

**执行流程**：
```
提交任务
  ↓
核心线程满？ → 否 → 创建核心线程执行
  ↓是
阻塞队列满？ → 否 → 入队等待
  ↓是
最大线程满？ → 否 → 创建临时线程执行
  ↓是
拒绝策略
```

**四种拒绝策略**：
| 策略 | 行为 |
|------|------|
| AbortPolicy（默认） | 抛出 RejectedExecutionException |
| CallerRunsPolicy | 提交任务的线程自己执行 |
| DiscardPolicy | 直接丢弃，不抛异常 |
| DiscardOldestPolicy | 丢弃队列中等待最久的任务 |

**常用线程池（Executors）的坑**：
- `newFixedThreadPool`：队列无界（`Integer.MAX_VALUE`），任务积压可能 OOM
- `newCachedThreadPool`：最大线程无界，频繁创建线程可能 OOM
- `newSingleThreadExecutor`：队列无界
- **推荐手动 new ThreadPoolExecutor**，避免这些陷阱

### 3.5 synchronized 原理

**对象头中的 Mark Word** 记录锁状态：

```
偏向锁 → 轻量级锁 → 重量级锁（锁升级，不可逆）
```

| 锁状态 | 描述 | 适用场景 |
|--------|------|---------|
| 无锁 | 无竞争 | — |
| 偏向锁 | 只在 Mark Word 记录线程 ID | 单线程重复访问 |
| 轻量级锁 | CAS 自旋 | 低竞争（线程交替执行） |
| 重量级锁 | 操作系统 mutex，阻塞/唤醒 | 高竞争（线程争用） |

**JDK 1.6 优化**：引入偏向锁、轻量级锁、锁粗化、锁消除。

### 3.6 volatile 关键字

**两个语义**：
1. **可见性**：一个线程修改 volatile 变量，其他线程立即看到
2. **禁止指令重排序**：在 volatile 变量前后插入内存屏障

**实现原理**：变量读写时通过 **lock 前缀指令**触发缓存一致性协议（MESI）。

**volatile 不能保证原子性**：
`count++` 需要"读-改-写"三步，volatile 只保证每次读取都是最新值，但 `count++` 不是原子的。需要原子性用 `AtomicInteger` 或 `synchronized`。

### 3.7 JVM 内存区域

```
线程私有         线程共享
┌─────────┐    ┌────────┐
│ 程序计数器 │    │  堆     │
│ 虚拟机栈  │    │ 方法区   │
│ 本地方法栈 │    └────────┘
└─────────┘
```

| 区域 | 存储内容 | 异常 |
|------|---------|------|
| 堆 | 对象实例、数组 | OutOfMemoryError |
| 方法区 | 类信息、常量、静态变量 | OutOfMemoryError |
| 虚拟机栈 | 局部变量表、操作数栈、方法出口 | StackOverflowError / OOM |
| 程序计数器 | 当前线程执行的字节码行号 | 无 |
| 本地方法栈 | 调用 native 方法时使用 | StackOverflowError |

### 3.8 GC 与垃圾回收

**判断对象存活**：
- **引用计数法**（有循环引用问题）
- **可达性分析**（GC Roots 向下搜索，不可达即死亡）

**GC Roots 包括**：
- 虚拟机栈（栈帧中的局部变量）引用的对象
- 方法区中静态属性、常量引用的对象
- 本地方法栈 JNI 引用的对象

**垃圾回收算法**：

| 算法 | 描述 | 适用 |
|------|------|------|
| 标记-清除 | 标记存活对象，清除未标记的 | 老年代（有碎片问题） |
| 标记-复制 | 将存活对象复制到另一半空间 | 新生代（Minor GC） |
| 标记-整理 | 标记存活对象，向一端移动 | 老年代（Full GC） |

**经典 GC 收集器**：

| 收集器 | 工作区域 | 算法 | 特点 |
|--------|---------|------|------|
| Serial | 新生代 | 复制 | 单线程，暂停所有用户线程 |
| ParNew | 新生代 | 复制 | Serial 的多线程版本 |
| CMS | 老年代 | 标记-清除 | 并发收集，停顿时长短，有碎片 |
| G1 | 整个堆 | 标记-复制 + 标记-整理 | 分区设计，可预测停顿时间 |

**G1 的分区设计**：
将堆分成约 2048 个 Region（1-32MB），每个 Region 可以是 Eden/Survivor/Old/Humongous。优先回收垃圾最多的 Region（Garbage First 名字的来源）。

### 3.9 类加载机制

```
加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载
```

**加载**：通过全限定类名获取二进制字节流，将静态存储结构转为方法区运行时结构，在堆中生成 Class 对象。

**双亲委派模型**：

```
启动类加载器（Bootstrap ClassLoader）— rt.jar
    ↑
扩展类加载器（Extension ClassLoader）— jre/lib/ext
    ↑
应用类加载器（Application ClassLoader）— classpath
```

**工作流程**：一个类加载器收到加载请求后，先委派给父类加载器加载，只有当父类加载器无法加载时才自己尝试。

**为什么要双亲委派**：
- 保证核心类库的安全（如 `java.lang.Object` 始终由 Bootstrap ClassLoader 加载）
- 避免类重复加载

## 四、MySQL 数据库

### 4.1 索引

**InnoDB 索引结构**：B+ 树

**B+ 树特点**：
- 只有叶子节点存数据，非叶子节点存索引
- 叶子节点形成有序双向链表，范围查询只需遍历叶子节点
- 树高度通常 2-4 层（每层可存上千个 key），查询稳定

**聚簇索引 vs 非聚簇索引**：

| | 聚簇索引 | 非聚簇索引（二级索引） |
|--|---------|-------------------|
| 叶子节点 | 存整行数据 | 存主键值 |
| 数量 | 表只能有一个 | 可以有多个 |
| 回表 | 不需要 | 需要（索引覆盖不需要） |

**索引分类**：
- **主键索引**：聚簇索引，不能为 NULL
- **唯一索引**：列值唯一，可为 NULL
- **普通索引**：加速查询
- **联合索引**：多列组合，遵循最左前缀法则
- **全文索引**：文本搜索

**最左前缀法则**：
联合索引 `(a, b, c)` 生效条件：
- `a`、`a,b`、`a,b,c`、`a,c`（走 a 列索引）✅
- `b`、`c`、`b,c` ❌（不走索引）

### 4.2 EXPLAIN 分析

```sql
EXPLAIN SELECT * FROM user WHERE account = 'xxx';
```

| 字段 | 说明 | 关键值 |
|------|------|--------|
| type | 访问类型 | system > const > eq_ref > ref > range > index > ALL |
| key | 实际使用的索引 | — |
| rows | 扫描行数（估计） | 越小越好 |
| Extra | 额外信息 | Using index（覆盖索引）、Using filesort（需优化）、Using temporary（需优化） |

**type 性能排序**：const > ref > range > index > ALL。type 为 ALL 是大规模表查询需要优化的信号。

### 4.3 事务与隔离级别

**ACID**：
| 特性 | 含义 | 实现机制 |
|------|------|---------|
| 原子性（A） | 事务要么全做要么全不做 | undo log |
| 一致性（C） | 事务前后数据保持一致 | 其他三个特性共同保证 |
| 隔离性（I） | 事务之间互不干扰 | MVCC + 锁 |
| 持久性（D） | 提交后的数据永久保存 | redo log |

**四种隔离级别**：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---------|------|-----------|------|
| READ UNCOMMITTED | ❌可能 | ❌可能 | ❌可能 |
| READ COMMITTED (RC) | ✅解决 | ❌可能 | ❌可能 |
| REPEATABLE READ (RR) | ✅解决 | ✅解决 | ❌可能 |
| SERIALIZABLE | ✅解决 | ✅解决 | ✅解决 |

- **脏读**：读到其他事务未提交的数据
- **不可重复读**：同一事务内两次读取同一行数据结果不同（被其他事务修改并提交）
- **幻读**：同一事务内两次范围查询结果集不同（被其他事务插入/删除数据）

**MySQL InnoDB 默认隔离级别**：REPEATABLE READ

**RR 如何解决幻读**：
- **MVCC 快照读**（SELECT）：通过 ReadView 保证只能看到事务开始前的数据
- **间隙锁（Gap Lock）** + 临键锁（Next-Key Lock）：当前读（SELECT FOR UPDATE）时锁住记录之间的间隙，阻止其他事务插入

### 4.4 MVCC（多版本并发控制）

**核心组件**：
1. **隐藏字段**：`DB_TRX_ID`（最后修改该行的事务 ID）、`DB_ROLL_PTR`（指向 undo log 的指针）
2. **undo log 版本链**：每行记录的所有历史版本通过链表串联
3. **ReadView**：事务执行快照读时生成的"可见性视图"

**ReadView 包含**：
- `m_ids`：活跃（未提交）的事务 ID 列表
- `min_trx_id`：活跃事务中最小的事务 ID
- `max_trx_id`：下一个要分配的事务 ID
- `creator_trx_id`：创建该 ReadView 的事务 ID

**可见性判断**：

```
DB_TRX_ID < min_trx_id    → 已提交，可见
DB_TRX_ID ≥ max_trx_id    → 将来事务，不可见
DB_TRX_ID 在 m_ids 中     → 未提交，不可见
DB_TRX_ID 不在 m_ids 中   → 已提交，可见
```

**RC vs RR 的 ReadView 区别**：
- **RC**：每次 SELECT 都生成一个新的 ReadView
- **RR**：事务中第一次 SELECT 生成 ReadView，后续复用

### 4.5 InnoDB 锁

**行锁类型**：
| 锁类型 | 说明 |
|--------|------|
| 共享锁（S） | `SELECT ... LOCK IN SHARE MODE`，允许其他事务读，阻止写 |
| 排他锁（X） | `SELECT ... FOR UPDATE` / UPDATE / DELETE，阻止其他读写 |

**间隙锁（Gap Lock）**：
- 锁定一个范围但不包含记录本身
- 用于 RR 级别防止幻读
- 例如 `WHERE id BETWEEN 10 AND 20`，锁住 (10,20) 的间隙

**临键锁（Next-Key Lock）**：
- 行锁 + 间隙锁 = 临键锁
- 锁定一个范围及其中的记录
- InnoDB RR 默认使用临键锁

### 4.6 SQL 优化常见手段

1. **避免 SELECT \***：只取需要的列
2. **合理建索引**：在 WHERE、JOIN、ORDER BY 涉及的列上建索引
3. **避免索引失效**：
   - 不要在索引列上使用函数（`WHERE SUBSTR(name, 1, 3) = 'abc'`）
   - 避免前导通配符（`LIKE '%abc'` 不走索引，`LIKE 'abc%'` 走索引）
   - 避免隐式类型转换（`WHERE account = 123`，account 是 varchar）
   - OR 两边必须都有索引
4. **分页优化**：大偏移量改用子查询或游标
5. **适当使用覆盖索引**：索引中已包含所需字段，无需回表

## 五、Spring 框架

### 5.1 IoC（控制反转）与 DI（依赖注入）

**IoC**：对象的创建和管理权交给 Spring 容器，而不是自己 new。
**DI**：容器将依赖自动注入到对象中。

**三种注入方式**：

```java
// ① 字段注入（不推荐，不利于测试和不可变对象）
@Autowired
private UserService userService;

// ② Setter 注入
@Autowired
public void setUserService(UserService userService) { ... }

// ③ 构造器注入（推荐）
private final UserService userService;
public UserController(UserService userService) {  // Spring Boot 3.x 可以省略 @Autowired
    this.userService = userService;
}
```

**推荐构造器注入的原因**：
- 对象初始化时就确定依赖，不可变（`final`）
- 便于单元测试（不需要反射）
- 避免循环依赖（编译/启动时就发现）

### 5.2 Bean 生命周期

```
实例化 → 属性赋值 → 初始化 → 使用 → 销毁
                        ↓
              Aware 接口 → BeanPostProcessor
              (BeanNameAware,   (postProcessBeforeInitialization
               ApplicationContextAware)   → init-method/@PostConstruct
                                          → postProcessAfterInitialization)
```

**详细步骤**：
1. 实例化：通过反射创建对象
2. 属性赋值：填充属性（DI）
3. **Aware 接口**：注入 BeanName、ApplicationContext 等
4. **BeanPostProcessor#before**：初始化前处理
5. **@PostConstruct / InitializingBean / init-method**：自定义初始化
6. **BeanPostProcessor#after**：初始化后处理（AOP 在此创建代理）
7. 使用：Bean 就绪
8. 销毁：@PreDestroy / DisposableBean / destroy-method

### 5.3 AOP（面向切面编程）

**核心概念**：
| 概念 | 说明 |
|------|------|
| JoinPoint | 被拦截的点（方法执行） |
| Pointcut | 切点表达式，定义哪些方法被拦截 |
| Advice | 通知，定义拦截后的逻辑（@Before、@After、@Around） |
| Aspect | 切面 = Pointcut + Advice |
| Weaving | 把切面织入目标对象的过程 |

**@Transactional 的 AOP 原理**：
1. Spring 为带 @Transactional 的类生成**代理对象**
2. 进入方法前，代理对象开启事务（`connection.setAutoCommit(false)`）
3. 方法执行成功 → 提交；抛出 RuntimeException → 回滚
4. 注意：**同类方法调用**（`this.methodB()`）不走代理，事务不生效

### 5.4 Spring 事务传播行为

```java
@Transactional(propagation = Propagation.REQUIRED)  // 默认：加入当前事务，没有则新建
```

| 传播行为 | 说明 |
|---------|------|
| REQUIRED | 加入当前事务，没有则新建（默认） |
| REQUIRES_NEW | 挂起当前事务，新建一个（内外事务互不影响） |
| SUPPORTS | 有则加入，没有则不开启事务 |
| NOT_SUPPORTED | 以非事务方式执行 |
| MANDATORY | 必须在事务中执行，否则抛异常 |
| NEVER | 必须不在事务中执行，否则抛异常 |
| NESTED | 嵌套事务（JDBC Savepoint） |

### 5.5 @Autowired vs @Resource

| | @Autowired | @Resource |
|--|-----------|-----------|
| 来源 | Spring | JSR-250（Java 标准） |
| 匹配方式 | ByType → ByName | ByName → ByType |
| 是否必须 | required=true（可设为 false） | 必须 |

### 5.6 Spring Boot 自动配置

**@SpringBootApplication = @Configuration + @EnableAutoConfiguration + @ComponentScan**

**自动配置原理**：
1. `@EnableAutoConfiguration` 导入 `AutoConfigurationImportSelector`
2. 从 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 加载 100+ 自动配置类
3. 每个配置类有 `@ConditionalOnClass`、`@ConditionalOnMissingBean` 等条件注解
4. 满足条件则加载配置，创建 Bean

**举例**：引入 `mybatis-spring-boot-starter` 后，`MybatisAutoConfiguration` 自动创建 `SqlSessionFactory`、`DataSource` 等 Bean。

### 6.1 排序算法对比

| 冒泡 | O(n²) | O(n²) | O(1) | ✅ |

| 希尔 | O(n^1.3) | O(n²) | O(1) | ❌ |
| 快排 | O(n log n) | O(n²) | O(log n) | ❌ |

**快排（三数取中优化）**：

```java
void quickSort(int[] arr, int l, int r) {
    if (l >= r) return;
    int i = l, j = r, pivot = arr[l + (r - l) / 2];
    while (i <= j) {
        while (arr[i] < pivot) i++;
        while (arr[j] > pivot) j--;
        if (i <= j) {
            int tmp = arr[i]; arr[i] = arr[j]; arr[j] = tmp;
            i++; j--;
        }
    }
    quickSort(arr, l, j);
    quickSort(arr, i, r);
}
```

### 6.2 常见手撕代码模板

**二分查找**：
```java
int binarySearch(int[] nums, int target) {
    int l = 0, r = nums.length - 1;
    while (l <= r) {
        int mid = l + (r - l) / 2;
        if (nums[mid] == target) return mid;
        else if (nums[mid] < target) l = mid + 1;
        else r = mid - 1;
    }
    return -1;
}
```

**反转链表**：
```java
ListNode reverseList(ListNode head) {
    ListNode prev = null, curr = head;
    while (curr != null) {
        ListNode next = curr.next;
        curr.next = prev;
        prev = curr;
        curr = next;
    }
    return prev;
}
```

**LRU 缓存**：
```java
class LRUCache {
    class Node { int key, val; Node prev, next; }
    HashMap<Integer, Node> map;
    int capacity;

    public LRUCache(int capacity) {
        this.capacity = capacity;
        map = new HashMap<>();
        // head 和 tail 是哨兵节点
        head = new Node(); tail = new Node();
        head.next = tail; tail.prev = head;
    }

    public int get(int key) {
        Node node = map.get(key);
        if (node == null) return -1;
        moveToHead(node);
        return node.val;
    }

    public void put(int key, int value) {
        Node node = map.get(key);
        if (node != null) {
            node.val = value;
            moveToHead(node);
        } else {
            node = new Node(key, value);
            map.put(key, node);
            addToHead(node);
            if (map.size() > capacity) {
                Node tail = removeTail();
                map.remove(tail.key);
            }
        }
    }
}
```

### 6.3 动态规划常见题型

| 类型 | 典型题目 | 状态定义 |
|------|---------|---------|
| 背包 | 0-1 背包、完全背包 | `dp[i][j]` = 前 i 个物品容量 j 的最大价值 |
| 最长子序列 | LIS、LCS | `dp[i]` = 以 i 结尾的最长递增子序列长度 |
| 区间 DP | 回文子串、石子合并 | `dp[i][j]` = 区间 [i,j] 的最优解 |
| 状态压缩 | 旅行商 | 用二进制位表示状态 |

**0-1 背包模板**：
```java
int knapsack(int[] w, int[] v, int C) {
    int[] dp = new int[C + 1];
    for (int i = 0; i < w.length; i++) {
        for (int j = C; j >= w[i]; j--) {  // 倒序
            dp[j] = Math.max(dp[j], dp[j - w[i]] + v[i]);
        }
    }
    return dp[C];
}
```
