# 图片与文件上传 — 面试知识点 + 项目实战

## 一、项目中的图片处理全景

```
前端上传 → ImageController → ImageServiceImpl → 本地磁盘 images/
                                                      ↓
WebMvcConfig 静态资源映射 ← 访问 /images/uuid.jpg
```

### 1. 控制层：ImageController

```java
@PostMapping
public Result<Map<String, String>> upload(@RequestParam("file") MultipartFile file) throws IOException {
    String url = imageService.uploadImage(file.getBytes(), file.getOriginalFilename());
    return Result.success(Map.of("url", url));
}
```

- 使用 `MultipartFile` 接收上传的文件
- 通过 `getBytes()` 获取文件内容字节数组
- 通过 `getOriginalFilename()` 获取原始文件名（用于提取后缀）
- 交由 Service 层处理，返回可访问的 URL

### 2. 服务层：ImageServiceImpl

```java
public String uploadImage(byte[] fileBytes, String originalFilename) {
    // 1. 确保目录存在
    Path uploadPath = Paths.get("images/");
    Files.createDirectories(uploadPath);

    // 2. UUID 重命名，保留原始后缀
    String ext = 提取后缀(originalFilename);
    String filename = UUID.randomUUID().toString() + ext;

    // 3. 写入磁盘
    Files.write(uploadPath.resolve(filename), fileBytes);

    // 4. 返回相对 URL
    return "/images/" + filename;
}
```

| 步骤 | 实现 | 目的 |
|------|------|------|
| 目录初始化 | `Files.createDirectories()` | 确保存储目录存在 |
| 文件名生成 | `UUID.randomUUID() + 后缀` | 防冲突、防路径遍历攻击 |
| 写入磁盘 | `Files.write(path, bytes)` | NIO 直接写入，简单高效 |
| 返回 URL | `"/images/" + 文件名` | 前端拼接即可访问 |

**后缀提取的细节**：

```java
// 需要考虑两个边界：
// 1. 文件名可能为 null
// 2. 文件名可能不带后缀（如 Makefile）
String ext = "";
if (originalFilename != null && originalFilename.contains(".")) {
    ext = originalFilename.substring(originalFilename.lastIndexOf("."));
}
```

只保留最后一个 `.` 之后的部分（含 `.`），避免文件名中多个点导致的越界问题。

### 3. 访问层：静态资源映射

```java
// WebMvcConfig.java
@Override
public void addResourceHandlers(ResourceHandlerRegistry registry) {
    registry.addResourceHandler("/images/**")
            .addResourceLocations("file:images/");
}
```

配置后，浏览器直接访问 `http://localhost:8080/images/uuid.jpg` 即可获取图片，无需专门的下载 Controller。

### 4. 配置层：multipart 限制

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 10MB       # 单文件最大 10MB
      max-request-size: 20MB    # 单次请求总大小最大 20MB
```

## 二、当前实现的不足之处（面试要能主动指出来）

| 问题 | 说明 |
|------|------|
| **无文件类型校验** | 任何人都能上传 `.exe`、`.jsp` 等危险文件，有安全风险 |
| **无代码层大小校验** | 只靠 Spring 全局配置，不支持按不同业务设不同限制 |
| **本地磁盘存储** | 项目重启不会丢（文件在磁盘上），但无法水平扩展 |
| **无清理机制** | 上传的文件永远不会被删除，磁盘终会写满 |
| **全量读入内存** | `getBytes()` 将整个文件加载到内存，大文件会导致 OOM |
| **无访问权限控制** | `/images/**` 是公开的，任何人都能访问所有图片 |

### 3.2 文件类型白名单校验

**方式一：Content-Type 校验（前置过滤，可伪造）**

```java
private static final Set<String> ALLOWED_TYPES = Set.of(
    "image/jpeg", "image/png", "image/gif", "image/webp"
);

if (!ALLOWED_TYPES.contains(file.getContentType())) {
    throw new BusinessException("不支持的文件类型");
}
```

**方式二：Magic Number 校验（真正可靠）**

每个文件类型的前几个字节是固定的，读取后校验比 contentType 头更可靠：

| 文件类型 | 魔数（十六进制） | 前几个字节（ASCII） |
|---------|-----------------|-------------------|
| JPEG | `FF D8 FF` | `ÿØÿ` |
| PNG | `89 50 4E 47` | `.PNG` |
| GIF | `47 49 46 38` | `GIF8` |
| BMP | `42 4D` | `BM` |
| ZIP/DOCX | `50 4B 03 04` | `PK..` |

```java
private static final Map<String, byte[]> MAGIC_NUMBERS = Map.of(
    "image/jpeg", new byte[]{(byte) 0xFF, (byte) 0xD8, (byte) 0xFF},
    "image/png",  new byte[]{(byte) 0x89, 0x50, 0x4E, 0x47},
    "image/gif",  new byte[]{0x47, 0x49, 0x46, 0x38}
);

public void validateMagicNumber(byte[] fileBytes, String expectedMime) {
    byte[] magic = MAGIC_NUMBERS.get(expectedMime);
    if (magic != null) {
        for (int i = 0; i < magic.length; i++) {
            if (fileBytes[i] != magic[i]) {
                throw new BusinessException("文件格式不匹配");
            }
        }
    }
}
```

### 3.3 按业务场景限制文件大小

```java
// 不同业务不同限制
Map<String, Long> SIZE_LIMITS = Map.of(
    "avatar", 2 * 1024 * 1024L,     // 2MB — 头像
    "image",  10 * 1024 * 1024L,    // 10MB — 普通图片
    "video",  100 * 1024 * 1024L,   // 100MB — 视频
    "doc",    20 * 1024 * 1024L     // 20MB — 文档
);

public void validateSize(byte[] bytes, String bizType) {
    long limit = SIZE_LIMITS.getOrDefault(bizType, 5 * 1024 * 1024L);
    if (bytes.length > limit) {
        throw new BusinessException("文件大小超过限制");
    }
}
```

### 3.4 流式上传（解决大文件 OOM）

当前问题：`file.getBytes()` 将整个文件加载到内存，上传 500MB 文件会导致堆内存溢出。

```java
// ❌ 当前方式：全量读入内存
byte[] allBytes = file.getBytes();  // 大文件 OOM

// ✅ 改进：流式处理
public String uploadStream(InputStream in, String originalFilename) {
    String filename = UUID.randomUUID().toString() + ext;
    Path target = Paths.get("uploads/", filename);
    // 通过 Files.copy 流式写入，不占用堆内存
    Files.copy(in, target, StandardCopyOption.REPLACE_EXISTING);
    return "/uploads/" + filename;
}
```

### 3.5 存储架构演进：从本地到云存储

```
本地磁盘（当前） → NFS 挂载 → 对象存储（OSS/S3/MinIO）
  开发简单        多机共享      高可用、CDN 加速
  无法扩容        有性能瓶颈     生产标准
```

**解耦设计**：项目中通过 `ImageService` 接口隔离了存储实现，如果后续要换成 OSS，只需要新增一个实现类，Controller 和其他业务代码都不用改。

```java
// 接口
public interface ImageService {
    String uploadImage(byte[] fileBytes, String originalFilename);
}

// 本地实现（当前）
@Service
public class LocalImageServiceImpl implements ImageService { ... }

// OSS 实现（未来只需要加这个）
@Service
@ConditionalOnProperty(name = "storage.type", havingValue = "oss")
public class OssImageServiceImpl implements ImageService {
    public String uploadImage(byte[] fileBytes, String originalFilename) {
        String key = UUID.randomUUID() + ext;
        ossClient.putObject("bucket", key, new ByteArrayInputStream(fileBytes));
        return "https://cdn.example.com/" + key;
    }
}
```

这就是**策略模式 + 依赖倒置**：高层（Controller）不依赖具体实现，只依赖抽象接口。

## 四、完整的企业级文件上传架构

```
请求
  │
  ├─ ① 参数校验：文件为空、文件名白名单
  │
  ├─ ② 安全校验：Content-Type、Magic Number、病毒扫描
  │
  ├─ ③ 业务校验：大小按场景限制
  │
  ├─ ④ 文件处理：图片缩放/裁剪/水印、视频转码
  │
  ├─ ⑤ 存储落地：本地磁盘 / OSS / MinIO
  │
  ├─ ⑥ 元数据入库：文件名、大小、类型、URL、上传者、上传时间
  │
  └─ ⑦ 返回 URL
```

## 五、面试可能追问的问题

### Q1: MultipartFile 的工作原理是什么？

Spring 的 `DispatcherServlet` 检测到请求的 Content-Type 为 `multipart/form-data` 时，由 `MultipartResolver`（通常用 `StandardServletMultipartResolver`）解析请求体，将每个 `name` 对应的部分解析为 `MultipartFile` 对象。Tomcat 默认将超过 1MB 的文件写入临时目录，否则存在内存中。

### Q2: 上传的文件名为什么不能用原始名？

两个原因：
1. **路径遍历攻击**：用户可能传 `../../etc/passwd` 这样的文件名，如果直接用拼接路径，可能覆盖系统文件
2. **冲突**：不同用户上传同名的文件会互相覆盖

所以必须用 UUID 或哈希值重命名。

### Q3: 上传大文件（如 1GB）怎么办？

当前实现直接 `getBytes()` 会导致 OOM。解决方案：

| 方案 | 适用场景 | 说明 |
|------|---------|------|
| 流式写入 | 一般上传 | 用 `file.getInputStream()` 配合 `Files.copy()` |
| 分片上传 | 超大文件（>100MB） | 前端切分，后端合并，支持断点续传 |
| 临时文件 | 需要多次处理 | 先写到临时目录再异步处理 |

### Q4: 如果让你给这个项目加上文件类型校验，你会怎么设计？

```
方式一：前端校验（用户体验）→ 后缀名判断
方式二：后端校验（安全防线）→ Content-Type + Magic Number 双重校验
方式三：深度校验（高安全）  → 尝试解析/渲染文件（如图片用 ImageIO 读取宽高）
```

生产环境至少要做到方式二。

### Q5: 如果图片上传到 OSS 之后，本地还需要保留吗？

不需要。OSS 本身是持久化存储，而且自带多副本冗余。本地保留一份反而增加了复杂度，除非有合规要求（如数据必须本地存一份备份）。上传流程改为：`MultipartFile → OSS → 返回 URL`，本地只做临时缓冲。
