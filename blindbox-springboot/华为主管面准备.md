# 华为主管面准备 — 基于 BlindBox 项目

---

## 一、项目技术深度（高频必问）

### 1. 请简单介绍一下你的项目

> 盲盒电商后端系统，基于 Spring Boot 3.4 + MyBatis + MySQL + Redis。核心业务是用户注册充值、概率抽奖、晒单社交。技术亮点在于**高并发场景下的库存扣减**和**双写一致性处理**。

### 2. 核心难点：抽奖（Draw）流程的并发安全

**这是你项目最有价值的考点，务必滚瓜烂熟。**

**问：抽奖是怎么保证不超卖的？**

答：采用 **Redis + DB 双层库存扣减** 策略：

1. **Redis 原子扣减（第一道防线）**：用 `DECR` 命令原子递减，O(1) 无锁竞争，判断是否 < 0 判断库存是否耗尽
2. **数据库乐观锁 CAS（第二道防线）**：`UPDATE blind_box SET stock = stock - 1, version = version + 1 WHERE id = ? AND version = ? AND stock > 0`，通过 `affected rows` 判断是否成功
3. **余额检查用 SQL 层面兜底**：`UPDATE user SET balance = balance - ? WHERE id = ? AND balance >= ?`，即使应用层检查有并发窗口，SQL 层也不会出现负余额

**问：如果扣了 Redis 但后续失败了怎么办？**

答：Redis 扣减在事务之外，如果后续步骤（余额不足、DB CAS 失败、创建订单失败）抛异常，会调用 `initStock()` 恢复 Redis 库存。这是 **best-effort 回滚**，不是严格分布式事务，但在实际业务场景下足够可靠。

**问：为什么不直接用数据库悲观锁（SELECT FOR UPDATE）？**

答：
- 悲观锁在高并发下会导致行锁等待，吞吐量低
- 乐观锁 + Redis 先行扣减，热点操作走 Redis（单线程、O(1)），DB 只在最后做一次 CAS 更新
- 项目中确实定义了 `selectByIdForUpdate` 方法，说明考虑过悲观锁方案，最终选择了更优的方案

**问：Redis 和 DB 的一致性怎么保证？**

答：严格来说是**最终一致性**而非强一致性：
- Redis 库存是"预扣"，DB 库存是"真实"
- 应用启动时 `StockInitializer` 从 DB 同步到 Redis
- 如果 Redis key 过期（TTL 1天），会从 DB 重新加载
- 极端情况下（Redis 扣减后、DB 写入前进程崩溃）可能出现短暂不一致，但概率极低且可通过定时对账修复

### 3. 点赞系统的写合并优化

**问：点赞是怎么做的？为什么不用直接写数据库？**

答：每点赞一次就写 DB，高频场景下 DB 压力大。采用 **Redis 计数器 + 批量刷写** 模式：

```
每次点赞 → Redis INCR（O(1)）
当计数达到 10（阈值）→ 批量写入 DB（UPDATE likes = likes + delta）
读取时 → DB值 + Redis delta = 实时准确值
```

- 写放大从 N 次降到 N/10 次
- 如果 Redis 数据丢失，最多丢 9 个赞（可接受的数据损失换取性能）
- 这是典型的 **write-coalescing** 模式，类似 WAL 的思路

### 4. 缓存策略

**问：你们用了哪些缓存？怎么处理缓存一致性的？**

答：采用 **Cache-Aside** 模式：

| 缓存项 | TTL | 场景 |
|--------|-----|------|
| 盲盒列表 | 5min | 高频读，低频变 |
| 盲盒详情 | 10min | 含奖品信息，变更时清除 |
| 用户信息 | 30min | 充值后主动清除 |
| 库存 | 1天 | 热数据，启动时预热 |
| 点赞计数 | 7天 | 写合并缓冲 |

一致性策略：**写时删除缓存**，读时重建。Redis 故障时 **优雅降级**——所有 Redis 操作都有 try-catch，失败时回退到 DB，不影响核心功能。

### 5. 认证方案

**问：为什么用拦截器（Interceptor）而不是 Spring Security Filter？**

答：
- Spring Security 的 Filter Chain 太重，引入了大量不需要的功能（CSRF、Session、各种 Filter）
- 我只需要 JWT 验证，用 `HandlerInterceptor` 更轻量、更可控
- Spring Security 仅用于提供 `BCryptPasswordEncoder` Bean
- 拦截器可以精确控制哪些路径需要认证、哪些放行

**问：JWT 的安全性怎么考虑的？**

答（诚实回答可以改进的点）：
- 当前签名密钥硬编码在代码中，生产环境应该用环境变量或配置中心
- 没有实现 token 刷新机制，7天过期后需要重新登录
- 没有 token 黑名单，无法主动踢人（可以加 Redis 黑名单实现）

## 二、工程能力考察（华为主管最爱问）

### 1. 你做这个项目遇到了什么困难？怎么解决的？

> **建议回答框架：STAR 法则**

**难点一：库存超卖问题**
- **Situation**：最初直接操作数据库扣库存，并发时出现超卖
- **Task**：需要保证高并发下库存扣减的正确性
- **Action**：引入 Redis 原子操作做第一层过滤，DB 乐观锁做第二层保障，失败时回滚 Redis
- **Result**：解决了超卖问题，单机 QPS 提升明显

**难点二：Redis 和 DB 的双写一致性**
- **Situation**：Redis 扣减和 DB 事务不在同一个系统中
- **Task**：需要保证两边数据一致
- **Action**：采用 best-effort 回滚策略，应用启动时全量同步，运行时 key 过期时按需加载
- **Result**：在可用性和一致性之间取得了合理平衡

### 2. 如果让你重新设计，你会怎么改进？

**这是展现思考深度的好机会：**

1. **CAS 重试机制**：当前 DB 乐观锁失败直接抛异常，应该加 3 次重试（项目文档里提到了但没实现）
2. **引入消息队列**：订单创建可以异步化，用 MQ 解耦，提高吞吐
3. **分布式锁替代乐观锁**：如果多机部署，可以用 Redisson 分布式锁
4. **API 版本控制**：加上 `/api/v1/` 前缀，方便后续迭代
5. **接口幂等性**：抽奖接口应该加幂等控制，防止网络重试导致重复扣款
6. **监控和链路追踪**：加入 SkyWalking / Micrometer，方便排查问题
7. **参数校验异常处理**：当前 Jakarta validation 异常被兜底为 500，应该单独处理返回 400 + 字段错误信息

### 3. 你怎么理解代码质量？

> 从项目中举例：

- **分层清晰**：controller → service → mapper，各层职责单一
- **接口与实现分离**：所有 Service 都是接口 + 实现，方便测试和替换
- **构造器注入**：不用 `@Autowired` 字段注入，更利于测试和不可变性保证
- **统一响应体**：`Result<T>` 封装所有返回，前端处理一致
- **DTO 与 Entity 分离**：请求 DTO 和数据库实体分开，不暴露内部结构
- **也有不足**：有一处 controller 直接调用了 mapper（BlindBoxController.detail），违反了分层原则

### 4. 你怎么做技术选型的？

| 选择 | 理由 |
|------|------|
| MyBatis 而非 JPA | SQL 可控性强，复杂查询（分页+JOIN）手写更直观 |
| Redis 做库存 | 单线程原子操作，无锁竞争，适合热点数据 |
| 乐观锁而非悲观锁 | 盲盒库存热点场景，乐观锁冲突率可控，吞吐更高 |
| JWT 而非 Session | 无状态，适合前后端分离，不依赖服务端存储 |
| HandlerInterceptor 而非 Filter | 轻量，只需 JWT 验证，不需要 Spring Security 的全套能力 |

### 5. 你对微服务有什么理解？如果要拆分这个项目怎么拆？

> 展示架构思维：

当前是单体应用，如果用户量增长可以拆分为：
- **用户服务**：注册、登录、充值、用户信息
- **商品服务**：盲盒管理、奖品管理、库存管理
- **交易服务**：抽奖、订单
- **社交服务**：晒单、点赞、评论
- **网关**：统一鉴权、限流、路由

拆分后库存管理需要分布式锁（Redisson），订单需要 MQ 保证最终一致性。

## 四、可能追问的技术细节

### Q: 你的乐观锁没有重试，这在生产环境可以吗？

> 诚实回答 + 改进方案

确实不行，这是项目的一个不足。理想方案是加 3 次重试循环，每次重试前重新读取 version：

```java
for (int i = 0; i < 3; i++) {
    BlindBox box = blindBoxMapper.selectById(id);
    int affected = blindBoxMapper.decreaseStock(id, box.getVersion());
    if (affected > 0) break;
    // 重试
}
```

### Q: 你的概率抽奖是真随机吗？能作弊吗？

- 使用 `Math.random()` 生成伪随机数，密码学级别不够安全
- 生产环境应该用 `SecureRandom` 或接入第三方公证的随机服务
- 概率数据存在数据库中，理论上运营可以修改——但有操作日志即可审计

### Q: 如果 Redis 挂了，你的系统还能用吗？

- **可以**。所有 Redis 操作都有 try-catch 降级：
  - 缓存失效 → 回退到 DB 直查
  - 库存扣减 → 直接走 DB 乐观锁
  - 点赞计数 → 直接写 DB
- 系统会降级但不会崩溃，这是 **graceful degradation** 的设计

### Q: 你的系统能扛多少并发？

- 单机瓶颈主要在 DB，乐观锁冲突率随并发上升
- 理论上 Redis 层可以扛 10w+ QPS（单线程原子操作）
- DB 层受限于连接池大小（默认 10）和事务耗时
- 如果要提升：加 Redis 集群 + DB 读写分离 + 消息队列异步化

### Q: 分布式环境下你的方案还有效吗？

- Redis 库存扣减在分布式下依然有效（共享 Redis 实例）
- DB 乐观锁在多实例下也有效（CAS 是数据库层面的）
- 需要改进的是：缓存清除需要广播（可以用 Redis Pub/Sub），避免各实例缓存不一致

4. **数字说话**：QPS、响应时间、数据量，有数字比泛泛而谈更有说服力
5. **体现主人翁意识**：用"我"而不是"我们"来描述你负责的部分
