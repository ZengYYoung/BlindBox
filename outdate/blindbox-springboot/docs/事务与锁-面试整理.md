# 事务与锁 — 面试知识点 + 项目实战

## 一、事务（Transaction）

### 1.1 四大特性 ACID

| 特性 | 含义 | 项目中的体现 |
|------|------|-------------|
| **A**tomictiy 原子性 | 事务内的操作要么全部成功，要么全部回滚 | `@Transactional` 确保 draw() 中扣库存、扣余额、创建订单任一失败全部回滚 |
| **C**onsistency 一致性 | 事务前后数据满足约束（余额不超扣、库存不超卖） | `balance >= #{amount}`、`stock > 0` 在 SQL 层面保证 |
| **I**solation 隔离性 | 并发事务互不干扰 | 锁机制实现，见下文 |
| **D**urability 持久性 | 提交后数据永久保存 | 写入 MySQL（InnoDB redo log 保证） |

### 1.2 隔离级别（MySQL InnoDB）

| 级别 | 脏读 | 不可重复读 | 幻读 | 默认 |
|------|------|-----------|------|------|
| READ UNCOMMITTED | 可能 | 可能 | 可能 | |
| READ COMMITTED | 避免 | 可能 | 可能 | |
| **REPEATABLE READ** | **避免** | **避免** | **可能（但 InnoDB 的 MVCC+间隙锁可避免）** | **MySQL 默认** |
| SERIALIZABLE | 避免 | 避免 | 避免 | |

项目中没有显式设置隔离级别，使用 MySQL 默认的 **REPEATABLE READ**。对于盲盒场景来说够用，因为 `FOR UPDATE` / 乐观锁本身提供了更强的互斥保证。

### 1.3 传播行为（Propagation）

`@Transactional` 默认 `REQUIRED`：支持当前事务，不存在则新建。draw() 方法被 OrderController 调用，调用端无事务，所以每次 draw() 会开启一个新事务。

## 二、锁（Lock）

### 2.1 乐观锁 vs 悲观锁

| | 悲观锁 | 乐观锁 |
|--|--------|--------|
| 思想 | 先锁再操作，别人进不来 | 先操作，提交时检查冲突 |
| 实现 | `SELECT ... FOR UPDATE` | version/CAS 字段 |
| 适用场景 | **高争用**（写冲突频繁） | **低争用**（写冲突少） |
| 优缺点 | 简单可靠，但并发吞吐低 | 吞吐高，但冲突时需重试 |

### 2.2 行锁（Record Lock）

`SELECT ... FOR UPDATE` 是 **行级排他锁（X锁）**：
- 锁住的是索引记录（InnoDB 基于索引加锁）
- 事务不提交，锁不释放
- 其他事务的 `FOR UPDATE`、`UPDATE`、`DELETE` 会被阻塞

### 2.3 MVCC（Multi-Version Concurrency Control）

InnoDB 通过 MVCC 实现 **快照读（Snapshot Read）**：
- 普通 `SELECT` 不加锁，读取的是事务开始时的快照版本
- `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 是**当前读（Current Read）**，读取最新提交版本
- MVCC 让读不阻塞写，写不阻塞读

### 2.4 间隙锁（Gap Lock）

REPEATABLE READ 级别下，`FOR UPDATE` 除了锁住现有记录，还可能锁住记录之间的间隙，防止幻读。

## 三、项目实战：盲盒抽奖的锁与事务演进

### 3.1 优化前架构

```
Controller → @Transactional draw()
  ├─ ① SELECT ... FOR UPDATE    ← 悲观行锁
  ├─ ② 检查余额
  ├─ ③ 概率抽奖（加权随机）
  ├─ ④ UPDATE stock (WHERE version=?)  ← 乐观锁 CAS
  ├─ ⑤ UPDATE balance
  └─ ⑥ INSERT order
```

**问题**：悲观锁和乐观锁同时使用，功能重叠。
- `FOR UPDATE` 已经让并发事务串行排队了，version CAS 永远不会检测到冲突（因为同一行上的写操作已经是串行的）
- 多了一层无意义的锁等待，降低吞吐

### 3.2 优化后架构

```
Controller → @Transactional draw()
  ├─ ① SELECT（普通查询，无锁）
  ├─ ② 检查余额
  ├─ ③ 概率抽奖（加权随机）
  ├─ ④ UPDATE stock (WHERE version=?)  ← 乐观锁 CAS × 最多3次重试
  │    ├─ CAS 成功 → break
  │    ├─ CAS 失败 → SELECT 最新 version 再试
  │    └─ stock=0 → 抛异常
  ├─ ⑤ UPDATE balance
  └─ ⑥ INSERT order
```

### 3.3 关键代码解析

**乐观锁扣库存（核心代码）**:

```java
for (int i = 0; i < 3; i++) {
    int affected = blindBoxMapper.decreaseStock(blindBoxId, box.getVersion());
    if (affected > 0) { stockSuccess = true; break; }
    // CAS 冲突，重新读取最新 version 再试
    box = blindBoxMapper.selectById(blindBoxId);
    if (box.getStock() <= 0) throw new BusinessException("库存已被抢完");
}
```

对应 SQL：

```sql
UPDATE `blind_box`
SET stock = stock - 1, version = version + 1
WHERE id = #{id} AND version = #{version} AND stock > 0
```

**为什么会 CAS 冲突**？例如两个请求同时读到 version=3：

```
时间线：
请求A: 读到 version=3 → UPDATE WHERE version=3 → 成功, version→4
请求B: 读到 version=3 → UPDATE WHERE version=3 → 影响0行 → 重新读到 version=4 → 重试成功
```

**为什么用悲观锁改乐观锁**？
- 盲盒抽奖是**写多读少**（很多人抢同一个盲盒），但每次写操作很快（毫秒级 UPDATE）
- 去掉 `FOR UPDATE` 后，并发请求不再排队阻塞等待行锁，吞吐更高
- 配合重试机制（3次），CAS 冲突基本都能成功，用户几乎感知不到

**原子扣余额**：

```sql
UPDATE `user` SET balance = balance - #{amount}
WHERE id = #{id} AND balance >= #{amount}
```

- 一条 SQL 完成"检查+扣减"，天然原子性
- `balance >= #{amount}` 在数据库层面兜底，防止超扣

### 3.4 为什么先抽奖再扣库存

```
① 概率抽奖（选奖品）
② 乐观锁扣库存（抢库存）
```

顺序很重要：先确定抽到什么奖品，再尝试扣库存。如果反过来，会出现"库存扣了但奖品没抽到"的回滚场景。**抽奖结果在事务开始时就确定了，只有库存抢到才算成功**，这符合盲盒"打开才知道是什么，但盒子的库存是先到先得"的业务逻辑。

## 四、面试可能追问的问题

### Q1: @Transactional 在方法内部调用不生效，为什么？

因为 Spring 的事务是通过 AOP 代理实现的。如果 `draw()` 内部调了本类的另一个 `@Transactional` 方法，那是一个普通方法调用（this.method()），不会经过代理，所以事务不生效。解决方案：
- 注入自己（`@Autowired` 本类）
- 把需事务的方法抽到另一个 Service

### Q2: 为什么没有处理 MySQL 死锁？

当前场景：
- 盲盒抽奖只操作 3 张表：`blind_box`（按 id 更新）、`user`（按 id 更新）、`orders`（INSERT）
- 都是单行操作，**不存在循环等待**的资源，所以不会死锁
- 如果批量更新且顺序不一致才可能死锁

### Q3: 重试 3 次后还是失败怎么办？

抛 `BusinessException("系统繁忙，请重试")`。前端收到后展示给用户，用户手动重试。更完善的方案是接入消息队列（如 RocketMQ）做异步重试，但当前场景下 3 次重试成功率 > 99.9%，用户手动重试已足够。

### Q4: 如果库存扣成功但扣余额/创建订单失败（事务回滚），库存会恢复吗？

会。`@Transactional` 保证所有操作在同一事务中，任何一步失败整个事务回滚，`UPDATE stock` 的改动也会被回滚到之前的状态。

### Q5: 怎么保证扣库存和抽奖结果是一对一的？

概率抽奖选出奖品后有 `prizeId`，后续创建订单时将 `order.prizeId = selected.id` 写入数据库。事务提交后，订单和奖品的关系是持久化的。**库存只保证"盲盒数量"，不关心盒子里是什么奖品**——即使拿到的奖品很稀有，库存也只会减 1。

## 五、扩展知识

### 5.1 更新丢失（Lost Update）

并发写时的经典问题：

```
事务A: 读到 stock=10 → 业务计算 → SET stock=9
事务B: 读到 stock=10 → 业务计算 → SET stock=9  ← A的更新被覆盖！
```

解决方案：
- 悲观锁：`SELECT ... FOR UPDATE`
- 乐观锁：version CAS
- 原子操作：`UPDATE ... SET stock = stock - 1`（不需要先读再算，推荐）

项目中使用了 `SET stock = stock - 1` 这种方式，即使不用 version 字段，也不会出现更新丢失，因为减库存是原子 SQL。version 字段的主要作用是**检测并发冲突**（让较早的请求失败重试，而不是默默覆盖）。

### 5.2 分布式锁 vs 数据库锁

当前项目是单体应用，数据库锁足够了。如果将来拆成微服务，多个实例同时抽奖，需要引入分布式锁（Redis Redisson / ZooKeeper），但这属于过早优化，当前不需要。
