## 三、核心技术点详解（含面试回答）

### 3.1 JWT 无状态认证

#### 实现

```java
// JwtUtil — 令牌生成
public static String generateToken(Integer userId) {
    return Jwts.builder()
            .claim("id", userId)
            .issuedAt(new Date())
            .expiration(new Date(System.currentTimeMillis() + 7 * 24 * 60 * 60 * 1000L))
            .signWith(KEY)  // HmacSHA256
            .compact();
}
```

```java
// JwtInterceptor — 令牌验证
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
    if ("OPTIONS".equals(request.getMethod())) return true;  // CORS 预检放行
    String authHeader = request.getHeader("Authorization");
    // 提取 Bearer token → 解析 userId → 设置到 request 属性
    Integer userId = JwtUtil.getUserId(token);
    request.setAttribute("userId", userId);
    return true;
}
```

```java
// WebMvcConfig — 拦截器注册 + 公开路径
registry.addInterceptor(jwtInterceptor)
        .addPathPatterns("/api/**")
        .excludePathPatterns("/api/auth/**", "/api/blindboxes", ...);
```

#### 面试回答要点

| 问题 | 回答 |
|------|------|
| **JWT 结构** | Header.Payload.Signature，三部分用 `.` 连接 |
| **Payload 能存密码吗** | 不能。Base64 只是编码不是加密，任何人都可解码 |
| **无状态怎么撤销** | 三种方案：Redis 黑名单、短时效 + refresh token、用户表 token 版本号 |
| **为什么用 Bearer** | RFC 6750 标准，axios/Postman 原生支持，网关统一识别 |
| **线程安全吗** | 安全。`request.setAttribute` 作用于每个请求独有的 request 对象 |

### 3.2 并发扣库存 — 乐观锁 + CAS 重试 ⭐ 高频

#### 核心代码

```java
// OrderServiceImpl.draw()
for (int i = 0; i < 3; i++) {
    int affected = blindBoxMapper.decreaseStock(blindBoxId, box.getVersion());
    if (affected > 0) {
        stockSuccess = true;
        break;
    }
    // CAS 失败：重新读取最新 version，重试
    box = blindBoxMapper.selectById(blindBoxId);
    if (box.getStock() <= 0) throw new BusinessException("库存已被抢完");
}
if (!stockSuccess) throw new BusinessException("系统繁忙，请重试");
```

```xml
<!-- BlindBoxMapper.xml -->
<update id="decreaseStock">
    UPDATE `blind_box`
    SET stock = stock - 1, version = version + 1
    WHERE id = #{id} AND version = #{version} AND stock > 0
</update>
```

#### 面试回答要点

**Q: 为什么用乐观锁而不是悲观锁？**

| | 悲观锁 (SELECT FOR UPDATE) | 乐观锁 (version CAS) |
|--|--------------------------|---------------------|
| 原理 | 查询时加行锁，其他事务等待 | 更新时校验版本号，失败重试 |
| 并发度 | 低（串行排队） | 高（CAS 失败立即返回） |
| 死锁风险 | 有 | 无 |
| 适用场景 | 写冲突极高 | 读多写少 / 冲突较低 |

盲盒抢购是典型的**读多写少**场景（大量用户浏览，少数人买到）。乐观锁在不持有数据库连接的情况下重试，资源利用率更高。

**Q: 重试 3 次够吗？**

3 次重试在中等并发下足够（CAS 竞争成功率 > 99%）。如果 3 次都失败，说明当前冲突极高，让用户重试比继续自旋更合理。极端高并发场景可以考虑：
- 改用 Redis 原子操作做库存扣减（Lua 脚本）
- 请求排队（消息队列）

**Q: `stock > 0` 条件不是多余的吗？有 version 就够了**

不多余。极端情况下 version 匹配但 stock 已为 0 的业务语义需要保障（如手动修改数据库、并发 bug 导致 version 不一致），双重校验是防御性编程。

### 3.3 概率抽奖算法 — 轮盘赌

#### 实现

```java
private Prize drawByProbability(List<Prize> prizes) {
    double rand = Math.random();
    double cumulative = 0.0;
    for (Prize p : prizes) {
        cumulative += p.getProbability().doubleValue();
        if (rand <= cumulative) return p;
    }
    return prizes.get(prizes.size() - 1);  // 兜底
}
```

#### 原理

```
奖品 A: 50%     奖品 B: 30%     奖品 C: 20%
0─────────0.5─────────0.8─────────1.0
    ↑ rand=0.35 → 命中 A
            ↑ rand=0.62 → 命中 B
```

每个奖品的概率映射到 [0, 1) 区间的一段，随机数落在哪个段就中哪个奖。最后一个奖品作为兜底是为了防止浮点数精度累加导致的 `cumulative < 1.0` 使 `rand` 落在空白区间。

### 3.4 Spring 事务管理

#### 项目中事务的使用

```java
// OrderServiceImpl.draw() — 整个方法一个事务
@Transactional
public Map<String, Object> draw(Integer userId, Integer blindBoxId) {
    // 扣库存、扣余额、创建订单 —— 要么全部成功，要么全部回滚
}
```

#### 面试扩展

**Q: @Transactional 的底层原理？**

AOP 代理 — 进入方法前开启事务（`autoCommit=false`），方法执行成功后提交，抛出 RuntimeException 时回滚。

**Q: 同一个类中方法 A 调用带 @Transactional 的方法 B，事务还会生效吗？**

**不会**。因为 Spring 的事务通过 AOP 代理实现，类内部调用不会经过代理，相当于 `this.methodB()`，事务注解被忽略。解决办法：将方法 B 拆分到另一个 Service，或通过 `AopContext.currentProxy()` 获取代理对象。

**Q: 项目中 draw() 用 @Transactional 够吗？**

当前足够了。但注意：乐观锁 CAS 失败重试时，整个事务会回滚，然后重新开启事务再试。如果读取最新 version 和重试 UPDATE 之间又发生了并发写入，这个设计其实有个小问题——重试时 `box.getVersion()` 读取的是最新版本，但事务隔离级别是 READ COMMITTED 时第二次读取可能读到旧数据。严格来说应该在重试循环内重新 `selectById` 获取 version。

### 3.5 全局异常处理

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BusinessException.class)
    public Result<?> handleBusinessException(BusinessException e, HttpServletResponse response) {
        response.setStatus(e.getCode());
        return Result.error(e.getCode(), e.getMessage());
    }

    @ExceptionHandler(Exception.class)
    public Result<?> handleException(Exception e, HttpServletResponse response) {
        response.setStatus(500);
        return Result.error(500, "服务器内部错误");
    }
}
```

受益于这种设计，业务代码中只需 `throw new BusinessException("xxx")` 即可统一处理错误响应，不需要在每个 Controller 中 try-catch。

### 3.6 统一响应结果

```java
@Data
public class Result<T> {
    private int code;    // 200 成功，400 业务错误，401 未登录，500 服务器错误
    private String msg;
    private T data;
}
```

前端统一按 `response.data.code` 判断请求是否成功。

### 3.7 图片上传与本地存储

#### 流程

```
MultipartFile → ImageServiceImpl → images/uuid.jpg → /images/uuid.jpg
                                  ↓
                         WebMvcConfig 静态资源映射 → 浏览器直接访问
```

#### 关键设计点

- **UUID 重命名**：防路径遍历攻击（`../../etc/passwd`）、防文件名冲突
- **静态资源映射**：`file:images/` → `/images/**`，无需专用下载接口
- **Multipart 配置**：单文件 10MB，单次请求 20MB

#### 面试追问

**Q: MultipartFile 工作原理？**

Spring 检测到 `Content-Type: multipart/form-data` 后，由 `StandardServletMultipartResolver` 解析请求体，每个 `name` 对应一个 `MultipartFile` 对象。Tomcat 默认将超过 1MB 的文件写入临时目录，否则存内存。

**Q: 大文件上传怎么办？**

当前 `file.getBytes()` 会将整个文件加载到内存，大文件可改用流式写入：

```java
public String uploadStream(MultipartFile file) {
    Files.copy(file.getInputStream(), target, StandardCopyOption.REPLACE_EXISTING);
}
```

100MB 以上需前端分片上传 + 后端合并。

| 问题 | 位置 | 风险 | 改进方案 |
|------|------|------|---------|

## 六、架构设计亮点总结

1. **分层清晰**：Controller（路由）→ Service（业务）→ Mapper（数据访问），各层职责单一
2. **接口隔离**：每个 Service 都有接口，便于替换实现（如 ImageService 可切换本地存储 → OSS）
3. **全局异常**：`BusinessException` + `@RestControllerAdvice`，业务代码无需 try-catch
4. **统一响应**：`Result<T>` 统一定义 code/msg/data 结构，前后端约定一致
5. **拦截器认证**：认证逻辑集中到拦截器，Controller 只管拿 userId，无需重复解析 token
6. **乐观锁并发**：CAS + version 控制库存扣减，比悲观锁并发度高

## 七、可能的面试追问

### Q1: 如果这个项目真正上线，你觉得最大的瓶颈在哪？

盲盒抢购瞬间的**库存扣减并发**是最大挑战。当前乐观锁 + 3 次重试在百级并发下没问题，万级以上并发建议引入 Redis 原子操作做前置库存扣减，MySQL 做最终一致性持久化。

### Q2: 如果让你重新设计这个项目的架构，会做什么改变？

1. **引入 Redis**：缓存热门盲盒信息、分布式锁、token 黑名单
2. **引入消息队列**：抽奖异步化，削峰填谷
3. **对象存储**：图片替换 OSS，支持 CDN 加速
4. **密码加密**：BCrypt 替代明文
5. **刷新令牌**：access token（2h）+ refresh token（7d）

### Q3: 你的概率抽奖算法能保证总概率等于 1 吗？

不能严格保证。浮点数精度累加可能导致 `sum < 1.0`。兜底逻辑（返回最后一个奖品）解决了这个问题。严格方案：最后一个奖品的概率用 `1 - sum(others)` 计算。

### Q4: 用户同时多个请求抽盒，余额会被多扣吗？

不会。因为 `@Transactional` 保证事务隔离，`decreaseStock` 和 `decreaseBalance` 在同一个事务中。更严谨地说，关键在于余额更新语句是否原子——如果 `updateBalance` 是 `SET balance = balance - price` 这种原子更新，就不会出错。当前实现：

```java
userMapper.decreaseBalance(userId, box.getPrice()); // 应该是 SET balance = balance - #{price}
```

需要确认 SQL 实现是原子扣减而不是读-改-写。

### Q5: 项目中没有使用 DTO 做数据脱敏，有什么问题？

当前 `UserService.getUserInfo()` 直接返回 `User` 实体，其中包含 `password` 字段（虽然是 null）。更好的做法是定义 `UserVO` 只返回需要的字段，或者用 `@JsonIgnore` 注解忽略敏感字段。

### Q6: 你们的项目是怎么处理密码的？为什么用 BCrypt？

当前是明文（待改进）。正确做法是用 `BCryptPasswordEncoder`：
- BCrypt 内置随机 salt，相同密码每次加密结果不同
- 可调迭代次数（强度），暴力破解成本极高
- MD5/SHA256 计算速度太快，已被彩虹表攻破

### Q7: 你怎么理解 RESTful？

RESTful 的核心是**资源导向**的 URL 设计和 HTTP 方法的语义化使用：

| 操作 | HTTP | 路径 |
|------|------|------|
| 获取盲盒列表 | GET | `/api/blindboxes` |
| 获取盲盒详情 | GET | `/api/blindboxes/{id}` |
| 创建盲盒 | POST | `/api/admin/blindboxes` |
| 删除盲盒 | DELETE | `/api/admin/blindboxes/{id}` |
| 创建订单（抽盒） | POST | `/api/blindboxes/{id}/draw` |

但 `draw` 放在 `POST /api/blindboxes/{id}/draw` 而不是 `POST /api/orders` 是考虑到前端调用习惯，属于实用性对 REST 纯正性的妥协。
