# BlindBox 项目分析 — 优缺点与实现难点

> 面向华为通用软件开发岗位面试准备，结合项目实际代码进行深度分析。

---

## 一、项目总述

盲盒电商平台后端，基于 Spring Boot 3.4.4 + MyBatis + MySQL + JWT，实现了用户注册登录、盲盒浏览与抽盒购买（含概率算法与库存并发控制）、晒单社区（点赞/评论）、图片上传、管理端 CRUD 等完整功能。

---

## 二、项目优点

### 2.1 架构分层清晰，遵循 Spring Boot 最佳实践

项目严格遵循 **Controller → Service → Mapper** 三层架构，职责划分明确：

- **Controller 层**：只负责参数校验、调用 Service、返回统一结果，不包含业务逻辑
- **Service 层**：定义接口 + Impl 实现类，业务逻辑集中于此，便于测试和替换
- **Mapper 层**：MyBatis XML 映射，SQL 与 Java 代码分离，复杂 SQL 可读性好

这种分层方式在团队协作和后期维护中优势明显，也是企业级 Java 项目的标准做法。

### 2.2 统一的异常处理和响应封装

- `Result<T>` 统一响应体：所有接口返回 `{ code, msg, data }` 格式，前端解析统一
- `BusinessException` 自定义业务异常：携带 HTTP 状态码，语义清晰
- `GlobalExceptionHandler`（`@RestControllerAdvice`）：全局捕获异常，避免 Controller 中大量 try-catch

```java
// 示例：Controller 中代码非常简洁
@PostMapping("/draw")
public Result<?> draw(@PathVariable Integer id, HttpServletRequest request) {
    Integer userId = (Integer) request.getAttribute("userId");
    return Result.success(orderService.draw(userId, id));
}
```

### 2.3 核心交易流程设计合理 — 乐观锁 + 条件更新

抽盒购买是项目最核心、并发最高的场景，实现方案体现了对并发安全的深入理解：

**库存扣减 — 乐观锁（CAS + 重试）：**
```sql
UPDATE blind_box
SET stock = stock - 1, version = version + 1
WHERE id = #{id} AND version = #{version} AND stock > 0
```
- 通过 `version` 字段实现 Compare-And-Set，无需加锁
- Java 层最多重试 3 次，每次重新读取最新 version
- 兼顾了性能和数据一致性

**余额扣减 — 条件更新：**
```sql
UPDATE user SET balance = balance - #{amount}
WHERE id = #{id} AND balance >= #{amount}
```
- 直接在 SQL 层面保证余额不会被扣成负数
- 即使并发场景下也不会出现超扣

**整体事务保障：** `draw()` 方法使用 `@Transactional` 注解，库存扣减、余额扣减、订单创建在同一事务中，任一失败整体回滚。

### 2.4 JWT 无状态认证方案

- 自定义 `JwtInterceptor` 实现认证，不依赖 Spring Security，项目轻量
- 通过 `WebMvcConfig` 精确控制哪些接口需要认证、哪些公开
- 用户信息通过 `request.setAttribute("userId", userId)` 传递，Controller 层获取方便
- Token 有效期 7 天，适合移动端/Web 端的长期登录场景

### 2.5 概率抽奖算法实现

```java
private Prize drawByProbability(List<Prize> prizes) {
    double random = Math.random();
    double cumulative = 0;
    for (Prize prize : prizes) {
        cumulative += prize.getProbability().doubleValue();
        if (random < cumulative) {
            return prize;
        }
    }
    return prizes.get(prizeList.size() - 1); // 兜底处理
}
```
- 经典的**轮盘赌算法**（Roulette Wheel Selection）
- 概率累加 + 随机数落点判定，时间复杂度 O(n)
- 最后一个奖品作为兜底，处理浮点精度问题

### 2.6 数据库设计规范

- 使用外键约束保证引用完整性（`ON DELETE CASCADE` 级联删除）
- 价格使用整数（分）存储，避免浮点精度问题
- 时间字段使用 `DEFAULT CURRENT_TIMESTAMP`，数据库层面自动管理
- 盲盒表预留 `version` 字段支持乐观锁

### 2.7 良好的编码习惯

- DTO 层使用 Jakarta Bean Validation（`@NotBlank`, `@NotNull`, `@Valid`）做参数校验
- Lombok 减少样板代码，提高开发效率
- MyBatis XML 中使用 `<if>` 动态 SQL 实现灵活查询
- 分页查询使用手动 offset/limit 计算，逻辑清晰

## 三、项目缺点与改进空间

### 3.1 安全性问题

| 问题 | 现状 | 改进方案 |
|------|------|----------|
| 密码明文存储 | 注册时直接存原文密码 | 使用 `BCryptPasswordEncoder` 哈希加密 |
| JWT 密钥硬编码 | Secret 写在源码中 | 读取环境变量或配置中心，生产环境用 RSA 非对称加密 |
| 无管理员权限校验 | `/api/admin/**` 任意登录用户可访问 | 用户表增加 `role` 字段，拦截器或注解鉴权 |
| 数据库密码明文 | `application.yml` 中明文存储 | 使用 `${DB_PASSWORD}` 环境变量注入，或 Jasypt 加密 |
| 无接口限流 | 抽盒接口可被恶意高频调用 | 引入 RateLimiter（Guava）或 Redis + 滑动窗口限流 |

### 3.2 并发场景存在隐患

**充值竞态条件：**
```java
// 当前实现：先读后写，存在并发问题
int newBalance = user.getBalance() + amount;
userMapper.updateBalance(userId, newBalance);
```
- 两个并发充值请求可能读到相同的旧余额，导致一次充值丢失
- **改进**：改用 `UPDATE user SET balance = balance + #{amount} WHERE id = #{id}` 原子操作

**点赞无唯一性校验：** 同一用户可无限次点赞
- **改进**：增加 `user_like` 关联表，点赞前检查是否已点赞

### 3.3 性能问题

**N+1 查询问题（订单列表）：**
```java
// 当前：查出 N 个订单后，每个订单再查 2 次（盲盒 + 奖品）= 1 + 2N 次查询
List<Order> orders = orderMapper.selectByUserId(userId);
for (Order order : orders) {
    BlindBox box = blindBoxMapper.selectById(order.getBlindBoxId());
    List<Prize> prizes = prizeMapper.selectByBlindBoxId(order.getBlindBoxId());
    // ...
}
```
- **改进**：使用 MyBatis `<association>` / `<collection>` 或 JOIN 查询一次获取

### 3.4 缺少单元测试

- 项目没有 `src/test` 目录，完全没有测试代码
- 核心的抽盒逻辑、概率算法、并发扣减等缺乏测试保障
- **改进**：至少为 `OrderService.draw()` 编写单元测试，Mock Mapper 层验证业务逻辑

### 3.5 文件上传安全性不足

- 未校验文件类型（MIME Type / 扩展名白名单）
- 未限制上传文件数量
- 文件存储在本地磁盘，不适合生产环境
- **改进**：增加文件类型校验、对接 OSS 对象存储（如阿里云 OSS）

### 3.6 可扩展性不足

- 用户体系过于简单，缺少角色/权限模型
- 订单状态只有"已支付"，缺少完整的状态机（待支付/已发货/已完成/已退款等）
- 没有使用配置中心或 profile 区分开发/生产环境

## 四、实现难点与解决方案

> 以下从大二学生的视角出发，分析在实现这个项目过程中最可能遇到的难点。

### 难点一：高并发下的库存扣减 — 如何防止超卖？

**问题描述：** 当多个用户同时抢购同一个盲盒时，如果简单地先查库存再扣减，会出现"超卖"（库存扣成负数）。

**学习过程：**
1. 最初可能想到的是直接 `UPDATE SET stock = stock - 1`，但这样无法判断库存是否够
2. 然后想到先 `SELECT stock` 判断再 `UPDATE`，但这是两步操作，并发下会出问题
3. 最终了解到**乐观锁**和**悲观锁**两种方案

**最终方案 — 乐观锁（CAS）：**
- 在盲盒表增加 `version` 版本号字段
- 更新时带上版本条件：`WHERE version = #{version} AND stock > 0`
- 更新成功：说明没人竞争，扣减成功，version + 1
- 更新失败（影响行数为 0）：说明有其他人先操作了，重新读取最新 version 重试
- 最多重试 3 次，仍然失败则提示"库存已被抢完"

**为什么选择乐观锁而非悲观锁（SELECT FOR UPDATE）：**
- 盲盒抢购是**读多写少**的场景，乐观锁冲突概率低
- 悲观锁会让其他请求排队等待，吞吐量下降
- 乐观锁无锁开销，适合高并发短事务

**面试话术：**
> "在抽盒场景中，我使用了基于 version 字段的乐观锁方案来解决超卖问题。SQL 层面通过 `WHERE version = #{version} AND stock > 0` 实现原子性的条件更新，Java 层面通过 CAS 重试机制处理并发冲突。相比悲观锁，乐观锁在读多写少的场景下性能更好，因为不需要加数据库行锁。同时我还对余额扣减做了条件更新 `WHERE balance >= #{amount}`，从数据库层面保证不会出现负余额。"

---

### 难点二：JWT 认证机制的实现 — 如何做到无状态登录？

**问题描述：** 传统的 Session 登录依赖服务器存储会话信息，集群部署时需要共享 Session。需要实现一种无状态的认证方式。

**学习过程：**
1. 了解 Session vs Token 的区别
2. 学习 JWT 的结构：Header.Payload.Signature
3. 理解 HMAC-SHA 签名机制
4. 实现拦截器进行 Token 校验

**实现方案：**

```
登录流程：
用户提交账号密码 → 验证通过 → JwtUtil 生成 Token → 返回给前端

请求流程：
前端携带 Token（Authorization: Bearer xxx）→ JwtInterceptor 解析验证
  → 验证失败 → 返回 401
  → 验证成功 → 将 userId 存入 request attribute → 放行到 Controller
```

**关键设计决策：**
- 选择 `HandlerInterceptor` 而非 Spring Security：项目功能简单，Spring Security 过于重量级
- Token payload 只存 `userId`：最小化 Token 体积，用户其他信息按需从数据库读取
- 7 天有效期：平衡安全性和用户体验
- 通过 `WebMvcConfig.addPathPatterns("/api/**").excludePathPatterns(...)` 精确控制认证范围

**面试话术：**
> "我选择了 JWT 而非 Session 来实现认证，因为 JWT 天然支持分布式部署，不需要服务端存储会话状态。我在自定义的 `JwtInterceptor` 中完成 Token 解析和校验，通过 `WebMvcConfig` 精确控制哪些接口需要认证。Token 中只存储 userId，避免暴露敏感信息。相比直接使用 Spring Security，自定义拦截器更轻量，也让我更深入地理解了认证的底层原理。"

---

### 难点三：概率算法的设计 — 如何保证概率准确且公平？

**问题描述：** 盲盒的核心是抽奖概率，需要保证：
1. 各奖品的中奖概率与设定值一致
2. 概率总和为 100%（或能正确处理不为 100% 的情况）
3. 浮点数精度问题不能导致某个奖品永远抽不到

**方案选择过程：**
1. 方案一：按概率生成多个"格子"，随机选格子 — 精度低，概率不连续
2. 方案二：直接用随机数判断 — 代码复杂，多奖品时嵌套 if 太深
3. 最终方案：**轮盘赌算法**（累加概率 + 随机数落点）

**实现细节：**
```java
// 概率分配示例（Sea 系列）：
// 普通款1: 0.30  → [0.00, 0.30)
// 普通款2: 0.30  → [0.30, 0.60)
// 稀有款1: 0.20  → [0.60, 0.80)
// 稀有款2: 0.15  → [0.80, 0.95)
// 隐藏款: 0.05  → [0.95, 1.00)
```

**浮点精度兜底：** 由于 `BigDecimal` 累加可能产生微小误差（如 0.9999...），最后一个奖品作为兜底返回，确保不会出现"什么都没抽到"的情况。

**面试话术：**
> "我使用轮盘赌算法实现概率抽奖，将所有奖品的概率按顺序排列，生成 [0, 1) 的随机数后沿概率轴查找落在哪个区间。这种方法的优点是时间复杂度 O(n)，且概率可以任意配置。我还处理了浮点精度兜底问题——当随机数恰好落在最后一个区间的边界外时，返回最后一个奖品。数据库中概率字段使用 DECIMAL(5,4) 保证精度。"

### 难点四：全局异常处理与统一响应 — 如何让接口返回格式一致？

**问题描述：** 如果每个 Controller 方法都自己 try-catch 并构造返回值，代码会非常冗余且不一致。

**解决方案：**
1. 定义 `Result<T>` 统一响应封装类
2. 定义 `BusinessException` 承载业务异常信息和 HTTP 状态码
3. 使用 `@RestControllerAdvice` + `@ExceptionHandler` 全局捕获

**异常处理链路：**
```
Controller 抛出 BusinessException(code=400, msg="余额不足")
    ↓
GlobalExceptionHandler 捕获
    ↓
设置 HTTP 状态码为 400，返回 Result.error(400, "余额不足")
    ↓
前端收到：{ "code": 400, "msg": "余额不足", "data": null }
```

**为什么不用 Spring 默认的错误处理：**
- Spring 默认返回 `{ timestamp, status, error, message, path }`，格式不统一
- 业务异常和系统异常混在一起，前端难以区分
- 自定义方案让前端只需判断 `code` 字段即可

**面试话术：**
> "我通过 `@RestControllerAdvice` 实现全局异常处理，业务层只需抛出 `BusinessException`，异常处理器会自动捕获并转换为统一的 `{ code, msg, data }` 格式返回。这样 Controller 层代码非常简洁，不需要 try-catch，也保证了所有接口的返回格式一致。对于参数校验异常，Spring Boot 的 `@Valid` 注解会自动抛出 `MethodArgumentNotValidException`，同样被全局处理器捕获。"

### 难点五：MyBatis 动态 SQL 与复杂查询

**问题描述：** 盲盒列表需要支持分页 + 按名称模糊搜索，订单查询需要关联多张表获取完整信息。

**实现方案：**

**动态 SQL 查询（盲盒列表）：**
```xml
<select id="selectAll" resultType="BlindBox">
    SELECT * FROM blind_box
    <where>
        <if test="name != null and name != ''">
            AND name LIKE CONCAT('%', #{name}, '%')
        </if>
    </where>
    ORDER BY created_at DESC
    LIMIT #{offset}, #{pageSize}
</select>
```

**晒单列表的 JOIN 查询：**
```xml
<select id="selectAll" resultType="PlayerShow">
    SELECT ps.*, u.username
    FROM player_show ps
    LEFT JOIN user u ON ps.user_id = u.id
    ORDER BY ps.created_at DESC
    LIMIT #{offset}, #{pageSize}
</select>
```

**遇到的问题与解决：**
- 问题：MyBatis 返回结果中 `username` 字段为 null
- 原因：`PlayerShow` 实体中 `username` 不是数据库字段，需要手动映射
- 解决：在 SQL 中通过 LEFT JOIN 获取，并确保 MyBatis 开启了 `map-underscore-to-camel-case`

**面试话术：**
> "我在 MyBatis 中大量使用了动态 SQL，比如 `<if>` 标签实现可选条件查询，`<foreach>` 实现批量插入。对于晒单和评论功能，我通过 LEFT JOIN 关联用户表获取用户名，避免了额外的查询。同时我理解了 MyBatis 的 `#{}` 和 `${}` 的区别——`#{}` 会预编译防 SQL 注入，`${}` 是直接拼接，我在所有用户输入的地方都使用 `#{}`。"

---

### 难点六：Spring Boot 拦截器链路设计

**问题描述：** 部分接口（如盲盒列表、注册登录）是公开的，部分需要认证。如何优雅地控制认证范围？

**设计方案：**
```java
@Override
public void addInterceptors(InterceptorRegistry registry) {
    registry.addInterceptor(jwtInterceptor)
        .addPathPatterns("/api/**")           // 拦截所有 /api/** 请求
        .excludePathPatterns(                  // 排除公开接口
            "/api/auth/**",                    // 登录注册
            "GET:/api/blindboxes",             // 盲盒列表
            "GET:/api/blindboxes/*",           // 盲盒详情
            "GET:/api/playershows/*/comments", // 评论列表
            "/api/images/**"                   // 图片上传
        );
}
```

**JWT 拦截器的细节处理：**
- 跳过 OPTIONS 请求（CORS 预检请求不能带 Token）
- 使用 `request.setAttribute` 传递解析出的 userId
- 捕获 JWT 解析异常，返回 401 而非 500

**面试话术：**
> "我通过 `WebMvcConfig` 配置拦截器链路，对 `/api/**` 路径统一拦截，然后用 `excludePathPatterns` 精确排除公开接口。在 JWT 拦截器中，我特别处理了 OPTIONS 预检请求的放行，否则 CORS 会失败。解析出的 userId 通过 request attribute 传递给 Controller，避免了在每个方法中重复解析 Token。"

## 五、面试高频追问与应对

### Q1: 为什么选择乐观锁而不是 Redis 分布式锁？

> "项目是单体架构，乐观锁直接利用数据库能力，不需要引入额外组件。如果未来需要扩展到多机部署，可以考虑 Redis + Lua 脚本实现分布式锁，或者使用 Redis 的 DECR 原子操作做库存预扣。"

### Q2: 为什么不直接用 Spring Security？

> "项目认证需求简单，只需要 JWT Token 校验，不需要角色/权限/Session 管理等 Spring Security 的完整功能。用 HandlerInterceptor 实现更轻量，也让我更深入理解了认证的底层机制。后续如果需要 RBAC 权限控制，可以平滑迁移到 Spring Security。"

### Q3: 事务的传播级别是什么？为什么？

> "使用默认的 `REQUIRED` 级别。`draw()` 方法中库存扣减、余额扣减、订单创建必须在同一事务中——要么全部成功，要么全部回滚。如果余额扣减失败但库存已扣减，没有事务回滚就会导致库存丢失。"

### Q4: 如何保证概率的公平性？会不会出现连续多次抽到隐藏款？

> "每次抽盒都是独立事件，理论上确实可能连续抽到隐藏款（概率 5%^n）。如果业务上需要保底机制（如 100 次必出隐藏款），可以增加一个计数器，达到阈值时强制触发隐藏款。这属于'保底机制'，是后续可扩展的方向。"

### Q5: 项目中有哪些可以优化的地方？

> "主要有三点：第一，订单查询存在 N+1 问题，可以用 JOIN 优化为单次查询；第二，充值操作存在竞态条件，应改为原子的 `balance + #{amount}`；第三，缺少单元测试，特别是核心的抽盒逻辑和并发场景。"
