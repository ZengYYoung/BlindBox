# 并发优化说明

实现更新：2026-10-13；文档校对：2026-10-19。源码、SQL和测试对应见 [关键技术文档](关键技术文档.md)。后端保持同步 MySQL 事务和库存驱动抽样；本轮没有增加 Redis 库存预占或异步订单，也没有修改数据库表结构。

## 1. 已完成的修改

| 原来的问题 | 当前实现 | 作用与边界 |
|---|---|---|
| 详情锁定奖池和奖品，与抽奖竞争 | 单条 LEFT JOIN 普通 SELECT，读取同一语句的 MVCC 快照 | 展示不申请库存写锁；抽奖仍使用锁定读 |
| 抽奖、补货使整个目录缓存失效 | 只缓存名称、系列、图片等商品元数据；每页批量查当前库存、状态和售价 | 抽奖/补货无需失效；展示库存仍只是读取时快照 |
| 同一热点池大量请求借用连接后等待行锁 | 在独立事务 Bean 外实行全局、同用户、同奖池准入 | 超额立即 503；单实例减少 JDBC 排队；跨实例仍靠 MySQL 锁 |
| JWT 查库早于入口保护 | JWT 前增加本机在途数限制和 Redis 来源限流 | 过载请求可以在认证查询前被拒绝 |
| 目录列表携带 JWT 时无必要地查用户 | 公开列表直接读取；登录/注册忽略旧 Bearer | 角色敏感接口仍检查当前数据库角色 |
| afterCommit 同步调用 Redis | 提交后只向有界单线程执行器提交失效任务，并合并重复任务 | Redis 延迟不延长提交回调；失效失败依赖缓存条目 TTL |
| 热点元数据缓存同时失效导致重复加载 | 固定 64 个锁条带，重查缓存、最多等 50ms | 同实例同条带一次加载；等待超时 503；跨实例可分别回源 |
| Redis 故障持续重试缓存网络访问 | 缓存故障后 1 秒冷却 | 冷却期间直接回源，仍受入口保护；限流故障策略另行处理 |
| 不存在的幂等记录锁定读可能产生间隙锁 | 父行锁取得后再普通读取幂等结果 | 用户/奖池锁串行化相同请求，避免额外索引间隙竞争 |
| 无法区分业务吞吐与拒绝流量 | 抽奖结果、耗时、准入拒绝、入口拒绝、缓存加载指标 | 不用用户 ID、奖池 ID 做指标标签，避免高基数 |

## 2. 交易边界与概率规则

请求路径：入口本机并发限制 → Redis 来源窗口 → JWT/当前角色 → Redis 用户写窗口 → DrawService 准入 → Spring 事务代理 → DrawTransactionService → MySQL。

DrawService 本身不启事务。准入通过后调用另一个 Spring Bean 的事务方法，避免同类内部调用绕过事务代理。许可在事务代理返回之后才释放，即覆盖提交、回滚和事务资源清理；异常路径也释放，重复关闭不重复释放。

事务仍按“用户 → 奖池 → 奖品”顺序锁定，取得用户锁后再查询已提交的同请求订单，再检查状态、余额和库存。选奖读取的是锁保护下的最新库存，概率仍为 stock_i / sum(stock)，同稀有度的概率为其各款库存之和 / 总量。条件扣减、订单和两种流水全部在同一事务内。

幂等记录查询采用普通读取，不对不存在的结果申请 FOR UPDATE 间隙锁。抽奖/充值/建池先锁用户，补货先锁用户再锁奖池；该幂等查询是本事务首次一致性读，快照建立在父锁取得之后，可以看到此前持有父锁的事务所提交的结果。不要在父锁取得前添加普通读取，也不要让新的写入口绕过父行锁；在 REPEATABLE READ 下提前建立的旧快照可能让重放查不到刚提交的记录。唯一键作为订单/资金流水的额外约束。

单实例默认一个奖池只接纳一个在途抽奖。其他请求快速返回 503，并带 Retry-After: 1；429 表示一分钟额度不足，带 Retry-After: 60。遇到 503、网络超时或结果未知，保留原 Idempotency-Key，优先查询 /api/orders/request/{key}，之后再用原 key 重试。不要将繁忙视为中奖失败后创建新 key。

并发重放不要求所有请求当场都返回 200：可能先返回 503，原事务完成后同 key 返回原订单。验收要求“最多一笔订单、一次扣款、一次扣库存”，并检查最终恢复结果。

## 3. 配置与启用

现有 .env 无需补参数即可使用默认值。需要调整时添加下列变量；启动器已允许这些键。

| 环境变量 | 默认值 | 含义 |
|---|---|---|
| DB_POOL_SIZE | 16 | 单实例最大 JDBC 连接数 |
| HTTP_MAX_INFLIGHT | 64 | /api/** 同时处理请求上限，不含 OPTIONS |
| DRAW_MAX_INFLIGHT | 8 | 在途抽奖上限；实际取 min(配置值, max(1, DB_POOL_SIZE/2))，整数除法 |
| DRAW_MAX_PER_POOL | 1 | 同奖池在途抽奖上限，同时不得超过全局上限 |
| ENTRY_READ_PER_MINUTE | 6000 | 同连接来源的 GET/HEAD 分钟额度 |
| ENTRY_WRITE_PER_MINUTE | 120 | 同连接来源其他写请求的分钟额度 |
| ENTRY_AUTH_PER_MINUTE | 20 | 同连接来源登录/注册合计分钟额度 |
| RATE_LIMIT_ENABLED | true | Redis 分钟额度开关；关闭后本机并发准入仍工作 |

用户维度额度保持：抽奖 10/min、开发充值 5/min、上传 6/min、其他写 30/min。来源额度和用户额度都需要通过；限流计数包含失败/繁忙尝试。计数达到 limit+1 后不继续增长，Lua 也修复缺失过期时间。固定窗口仍可能在边界突发。

HTTP 上限、JDBC 数、每分钟额度均不是 QPS 承诺。默认给抽奖留下最多半数 JDBC 预算，但认证、读请求、管理员操作仍共享连接池；这不是物理独占连接分区。调大并发值可能增加锁等待，不会提高同一库存行的更新能力。

来源使用真实连接 remoteAddr，不信任任意 X-Forwarded-For。Vite/Nginx 代理后来源可能聚合成代理 IP，ENTRY_* 是该来源的合计额度。单机开发保持默认；生产多用户部署需配合可信代理和网关设计来源识别与额度，不能直接把客户端转发头当身份。本项目 Nginx 模板有独立浏览器 IP 限流。多实例的分钟额度共享 Redis，而并发准入分别计算。

停止原来运行的后端，再启动新代码（前端接口地址不变）：

~~~bash
cd /Users/zengyy/code/blindbox
python3 scripts/run-backend.py --jar
~~~

--jar 使用已经打包的当前产物。修改源码后先执行：


## 4. 缓存一致性和故障策略

元数据 key 使用 blindbox:catalog:metadata:v2:<generation>:<查询条件>，条目 TTL 为 120 秒。generation 缺失时使用时间值初始化，减少驱逐版本标识后复用旧 key 的风险。创建、编辑、上下架或归档提交后异步递增版本；旧 key 由 TTL 回收。

每次列表查询另用一条按 ID 批量的 SQL 取得库存、售价和状态，过滤已经下架的条目，避免以缓存旧价格引导下单。缓存命中不会直接返回库存旧值，也不会修改缓存 map。新上架商品、名称、图片、搜索匹配及分页 total 在异步失效生效前可能仍旧；失效失败靠条目 TTL 恢复。metadataAsOf 与 asOf 分别描述元数据和本次查询。管理员列表直接查库。

详情为一条普通 SELECT，奖池与奖品来自同一语句快照；不会混合“抽奖前总库存”和“抽奖后各款库存”。不等于永远最新，也不保证浏览器看到的概率和稍后成交相同。成交重新锁定读取实际剩余量。

Redis 故障：公开读可以回源，仍有本机在途限制和目录加载限制；Redis 限流开启时写请求返回 503。异步缓存失效失败不会把已提交的商品更新错误报告为交易失败。目录等待繁忙、抽奖准入繁忙、数据库事务异常均不能自动跳过检查。

## 5. 观察指标

/actuator/metrics 及子路径要求 ADMIN；health 维持公开。Nginx 模板只转发业务路径，生产监控需通过受控内网访问或另配置受保护的指标入口。

| 指标 | 用途 |
|---|---|
| blindbox.draw.active / blindbox.draw.limit | 当前在途交易和实际全局预算 |
| blindbox.draw.admission.rejected | 按 user/pool/global 查看准入瓶颈 |
| blindbox.draw.results | committed、replayed、busy、rejected、error |
| blindbox.draw.duration | 包含准入和事务提交的服务耗时；过滤器提前拒绝不计入 |
| blindbox.http.active | 入口同时处理数 |
| blindbox.http.entry.rejected | concurrency、rate、redis |
| blindbox.http.entry.redis_errors | 来源限流故障 |
| blindbox.catalog.cache / loads / invalidations | 命中、回源、加载繁忙及失效状态 |
| hikaricp.connections.* / http.server.requests | 连接借用等待与 HTTP 请求耗时（需实际流量后查看） |

当前通过 Actuator 查询聚合指标；未增加 Prometheus 注册器或部署监控系统。publishPercentileHistogram 不等于 Actuator JSON 自动提供完整 P95/P99。端到端分位延迟用 k6 测量；接入相应监控后可导出直方图。只看 http_req_duration 而忽略 committed 数量，会把快速拒绝误当成吞吐提升。

## 6. 验证与后续压测

离线单测检查：50 个同时请求同池只有一个拿到许可，其他立即被拒绝；事务提交阻塞期间许可仍被持有，提交成功/失败之后均释放；详情只调用非锁定快照 SQL；目录动态字段不使用缓存旧值；缓存加载合并、回滚不失效、提交后排队、Redis/线程池异常；JWT 前拦截和权限。

这些测试使用 Mockito、真实 Spring 事务代理和可控的测试事务管理器，没有通过真实 MySQL 并发写入证明不超卖。验收记录另区分只读联调和交易验收。

只在独立测试库运行 scripts/draw-load.js。为每个并发用户准备不同账号、足够余额，并单独创建高库存测试池。脚本支持 BOX_ID 或 BOX_IDS；必须填写每次运行不同的 RUN_ID。

~~~bash
RUN_LOAD_TEST=YES RUN_ID=run-20261013-01 USER_TOKENS=token1,token2 BOX_IDS=101,102 VUS=2 ITERATIONS=100 k6 run scripts/draw-load.js
~~~

至少比较：一个热门池、多池多用户、读写混合、过载、Redis 故障、两后端实例。先保持限流启用验证保护，再在隔离环境关闭 Redis 分钟额度测处理链路；本机准入仍有效。逐档增加负载，记录 committed TPS、重放、业务冲突、429、503、P95/P99、JDBC 等待、数据库锁等待和 CPU。一次快速拒绝并不算成功抽奖。

压测前后运行 scripts/audit.sql，并检查钱包期初/期末、订单增量、库存增量；压测脚本无法代替数据库对账。不要直接用已导入的 400 个正常商品库存测售罄。无实测结果时不宣称千级、万级 QPS。

官方依据：[MySQL 一致性读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)、[Spring 提交回调资源生命周期](https://docs.spring.io/spring-framework/docs/6.2.x/javadoc-api/org/springframework/transaction/support/TransactionSynchronization.html)、[Redis Lua 原子执行](https://redis.io/docs/latest/develop/programmability/eval-intro/)。
