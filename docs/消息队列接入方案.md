# RabbitMQ 接入与站内通知

当前实现使用 Spring AMQP、RabbitMQ 和 MySQL Outbox。抽奖成功后，账户页的「抽奖通知」展示最近 30 条通知；通知异步产生，可能延迟。历史订单不会自动补发通知。

## 流程和业务边界

1. `DrawTransactionService.draw` 在原有 MySQL 事务内锁定用户、奖池与奖品，根据各奖品**当前剩余数量**抽样，扣余额及库存，写订单、流水和 `outbox_event`。任一步骤失败，事务回滚；同一请求 ID 重放不产生第二个事件。
2. `OutboxPublisher` 周期性租用一条待发送记录（30 秒租约），发送持久消息；发布确认为 ACK 且没有 mandatory return 时，才将事件标记 SENT。发送失败、确认超时或不可路由时以指数退避重试，最多间隔 300 秒。实例崩溃时租约到期可重新领取；确认或租约竞态可能造成重复投递。
3. `DrawNotificationConsumer` 从队列读取事件。`NotificationService.create` 在事务内读取订单快照并写通知，`notification.event_id` 唯一约束去重；监听方法正常返回后 Spring AMQP ACK。消费失败最多尝试 3 次（1 秒、2 秒间隔），再拒绝并转入死信队列，需人工排查和重投。
4. 登录用户通过 `GET /api/user/notifications` 查询本人最近 30 条通知，账户页可手动刷新。订单、余额和库存由数据库同步确定，不依赖通知是否生成。

发布确认不表示消费完成；物理消息允许重复，业务通知按 event_id 去重。普通死信转发并非端到端无损保障：死信交换机/队列故障也可能造成消息无法保留。当前实现尚无死信自动重放、后台管理、告警、容量清理或多节点高可用；不能声称达到生产级消息可靠性。接入 MQ 不会消除同一奖池数据库锁竞争，也没有经过生产压力测试。

## 本机 Homebrew 配置

启动服务：`brew services start rabbitmq`；管理页面：<http://127.0.0.1:15672/>。开发机新安装时本机通常可使用 `guest` / `guest`。远程或正式环境请使用专用账户与 vhost、最小权限和 TLS，不要暴露默认账户或将密码提交 Git。

在本机 `blindbox-springboot/.env` 中添加以下配置（已在 `.env.example` 和启动器白名单中提供）。本机默认 guest 时可省略账号、密码及 vhost，建议后续改用专用账户：

```dotenv
RABBITMQ_ENABLED=true
RABBITMQ_HOST=127.0.0.1
RABBITMQ_PORT=5672
RABBITMQ_USERNAME=guest
RABBITMQ_PASSWORD=guest
RABBITMQ_VHOST=/
```

**先备份现有数据库**，确认用户具备 Flyway 建表权限。重启 Spring Boot 时 Flyway 将执行 V5，创建 `outbox_event` 和 `notification`；本机 `.env` 不应提交或发到聊天。设置 `RABBITMQ_ENABLED=false` 可关闭发布和消费，但新抽奖依然会写入 outbox，后续启用后会处理积压。MQ 故障期间仍依赖数据库可用，通知会延迟。RabbitMQ health 在启用后参与应用健康检查，因此 MQ 故障可能使 health 显示 DOWN。

使用项目原有 `scripts/run-backend.py` 启动后端、启动前端，并登录账户查看「抽奖通知」。切勿在现有正式或珍贵库存上做反复测试：请准备隔离测试数据库和测试奖池。管理界面可查看 `blindbox.draw.notification.v1` 和 `blindbox.draw.notification.dead.v1` 的堆积；死信必须先排查根因再谨慎重新发布，消息原始 ID 不变才能继续去重。

## 故障排查和后续工作

- 无通知：确认 RabbitMQ 正常、配置已启用并重启后端；检查 outbox 的 `status`、`attempts`、`next_attempt_at`，以及队列和应用日志。`SENT` 只代表发布确认和成功路由，不代表通知已消费。
- `PENDING` 增长：检查网络、账号/vhost 权限、交换机绑定和 publisher confirms。单实例当前每次只领取一条，每轮默认间隔 500ms，是保守设置；需要压测并改进批量与监控后才能判断吞吐。
- 死信增长：检查消息体、订单是否存在和 MySQL 是否可用；目前没有自动重试死信或自动告警。
- 临时开发库集成测试需自行准备隔离 MySQL，`RabbitDatabaseIntegrationTest` 固定连接 `127.0.0.1:33319/blindbox_mq_test` 且会写数据并创建触发器，**严禁指向现有数据库或复用已有数据**；只有设置 `RUN_MQ_DB_TEST=YES` 才执行。`MessagingTest` 的真实 Rabbit 测试需 `RUN_RABBIT_TEST=YES`，使用随机临时队列并清理。

生产化还需要：Outbox 积压/失败/最老事件时间与死信监控、可审计的重投工具、保留期与归档、可靠死信方案、队列容量、分片和压测、节点/网络故障演练及部署权限控制。[RabbitMQ 官方确认机制](https://www.rabbitmq.com/docs/confirms)说明发布确认和消费确认各自的边界。
