# BlindBox 项目介绍与面试指南

2026-10-19校对。实现、SQL和测试的逐项对应见 [关键技术文档](关键技术文档.md)；旧版本资料已移至 [outdate](../outdate/README.md)。

## 1. 项目定位与真实完成范围

BlindBox 是一个基于 React、Spring Boot、MyBatis、MySQL 和 Redis 的收藏型盲盒 Web 项目，包含商品探索、账户与开发充值、抽奖、订单、收藏汇总、晒单评论、点赞、图片上传和管理配货。核心是“有限实体奖池，无放回抽样”：概率由剩余数量动态计算。

已实现：业务源码、服务端权限、同步事务、幂等流水、Redis缓存/限流、数据库迁移、前端重构、离线测试与接入模板。后续已按要求导入本机 MySQL 商品数据；2026-10-13 完成并发优化和只读 API 联调，实际抽奖写压测、跨实例故障验收和部署尚未执行。真实支付、物流退款、MQ异步落库和Redis库存预占是后续方向，不作为已实现亮点。

简历可写“设计并实现库存驱动抽奖及幂等交易链路”，联调通过前不要写“已验证零超卖”“支撑万级QPS”“生产上线”。

## 2. 使用方式与功能路径

1. 按接入指南连接 MySQL/Redis，启动 Spring Boot 和 Vite。
2. 注册用户；管理员角色通过受控数据库操作配置。
3. 管理员建奖池：价格、系列、奖品款式、图片、稀有度与实体数量；保存后上架。
4. 用户浏览详情，查看剩余数量和概率；开发模式可增加演示余额。
5. 点击抽奖，前端先保存请求ID，再发送请求；后台完成事务后返回中奖款和订单号。
6. 查看订单和收藏；社区可上传真实图片、发帖、评论、点赞/取消。
7. 管理员编辑商品信息、补货、下架或归档，不删除历史订单依赖的奖品。

预览模式只展示样例目录，用于看界面；它不证明后端可运行或实际抽奖正确。

## 4. 核心抽奖设计

### 4.1 概率含义

设第i款剩余库存为 s_i，总量 N=Σs_i：

- P(第i款)=s_i/N。
- P(某稀有度)=该稀有度所有款式的库存之和/N。
- N=0时拒绝抽奖，某款库存0时它占0个区间，无法被选中。

例：普通60、稀有30、隐藏10，隐藏初始概率10%。抽走一个隐藏后为9/99≈9.09%；抽走一个普通后为10/99≈10.10%。这不是每次都固定10%的独立有放回抽样。

### 4.2 整数区间算法

奖品A=3、B=2、C=1，总量6。生成随机整数ticket∈[0,6)：

| 票号 | 奖品 |
|---|---|
| 0、1、2 | A |
| 3、4 | B |
| 5 | C |

~~~java
long ticket = secureRandom.nextLong(totalStock);
long cumulative = 0;
for (Prize prize : prizes) {
    cumulative += prize.getStock();
    if (ticket < cumulative) return prize;
}
~~~

算法O(k)时间、O(1)额外空间，k是奖品款式数；不展开N个实体对象，不依赖浮点累加，不将最后一个奖品作为异常兜底。随机源使用SecureRandom，但安全随机不等于可公开验证的抽奖；当前没有随机承诺、第三方审计或可验证公平协议。

### 4.3 为什么必须和并发控制一起设计

仅修改概率公式仍不够。若两个请求同时用同一旧库存计算，随后扣减时发生冲突，再只重抽某个奖品，实际分布可能偏离库存比例。

实现把“读最新库存→选奖→扣减”放在锁保护下。同一奖池每一笔成功事务看到前一笔提交后的状态。失败事务回滚库存和资金；库存改变后再抽奖才会重新计算概率。

## 5. 抽奖事务、幂等与高并发机制

### 5.1 完整事务

~~~mermaid
sequenceDiagram
  participant U as 浏览器
  participant A as API/限流
  participant G as DrawService准入
  participant T as DrawTransactionService
  participant D as MySQL
  U->>A: POST draw + Idempotency-Key
  A->>G: 已认证请求
  G->>G: 同用户/同池/全局准入
  G->>T: 通过Spring事务代理调用
  T->>D: 锁用户行
  T->>D: 查同用户同requestId订单
  alt 已处理
    D-->>T: 原订单
    T-->>U: 原结果
  else 新请求
    T->>D: 锁盲盒行及奖品库存
    T->>T: 校验总量，整数区间选奖
    T->>D: 条件扣余额/奖品/总库存
    T->>D: 写订单、资金流水、库存流水
    T->>D: 提交事务
    T-->>U: 中奖结果
  end
~~~

任何更新影响行数不为1都抛业务异常，触发回滚。SQL余额条件也必须检查影响行数，否则“余额没扣成功、订单却创建了”的漏洞仍然存在。

### 5.2 固定锁顺序

抽奖先锁用户再锁奖池；创建/补货涉及操作者流水，也先锁用户再操作商品。同一用户多个请求串行，避免透支和重复处理。同一奖池多个用户按数据库行锁排队，不同用户的不同奖池可并行。

抽奖读取奖品使用 FOR UPDATE，即当前读取；选奖与扣减位于锁保护内。详情改为单条 LEFT JOIN 普通 SELECT，用同一语句的 MVCC 快照同时读取总库存与各款库存，避免浏览行为争抢库存写锁。查询快照只描述当时状态，成交仍重新锁定读取。

同实例先做全局/同用户/同池准入，超额立即503，不为等待热门池占用 JDBC。准入与事务在不同 Bean，许可覆盖事务提交或回滚后的清理。默认同池1、全局8，全局不超过连接池一半；跨实例仍由 MySQL 锁、唯一键和事务保证一致性。

### 5.3 幂等不是“禁止重复点击”

前端禁用按钮只是交互。真正保证来自：

- 用户行锁下普通查询已处理请求，首次一致性读在父锁取得后建立快照，减少不存在结果的间隙锁。
- orders唯一键(user_id,request_id)。
- 请求ID重复时返回同一个订单。
- 相同请求ID换盲盒返回409。
- 前端持久化未确认请求；网络超时后查询或同ID重试。
- 开发充值资金流水唯一键(user_id,type,request_id)。
- 管理建池唯一键(creator_id,create_request_id)与配置摘要。
- 补货按奖池和请求ID查询原流水，核对奖品和数量。

本项目使用“事务内完成处理”模式，没有先提交一个永久PROCESSING状态。查询404只表示当前尚未观察到已提交结果，不足以证明此前请求永远失败；客户端保留原ID。

### 5.4 Redis限流

Lua把计数和TTL检查合并执行，修复缺失过期时间；计数饱和至limit+1，持续拒绝不无限增长。固定窗口60秒，按用户/连接IP与业务作用域分key，多实例共享Redis就共享额度。Lua原子性仅覆盖Redis本身，不跨MySQL。

Redis限流启用时不可用，受保护写请求503；缓存不可用可以回源。二者故障策略不同，是根据数据与保护角色决定的，不是统一捕获异常后继续执行。

### 5.5 吞吐边界与后续扩展

当前属于“同步单体、数据库事务、热点池串行”的可靠基线，没有实测QPS。入口限流早于JWT查库，公开商品列表省去身份查询；库存批量查询、详情无锁、元数据缓存和事务前准入减少无效排队。角色敏感接口仍查当前用户。准入降低过载时资源占用，不等于提升单一库存行的物理更新能力。配置和指标见 [并发优化说明](并发优化说明.md)。

扩展顺序：采集锁等待和接口延迟→优化事务与索引→合理连接池和线程预算→独立奖池/批次→评估Redis原子预占或异步队列。拆分奖池会改变抽样范围，必须重新定义业务概率。

Redis预占需要持久预占ID、确认/取消、超时恢复、对账和单一库存事实管理；MQ需要本地事务outbox、投递重试、消费幂等、失败补偿。仅增加分布式锁或MQ依赖不能自动获得一致性。

## 6. Java与前端数据结构

| 数据结构 | 用途与复杂度 |
|---|---|
| List<Prize> | 按稳定顺序累计库存，抽取O(k) |
| LinkedHashMap | 保持API展示字段/稀有度统计顺序 |
| Map<String,Long> | 按稀有度聚合库存，平均O(1)更新 |
| Record请求DTO | 明确输入字段，Bean Validation限制范围 |
| long金额 | 单位分，避免二进制小数误差 |
| SecureRandom | 生成有界整数票号 |
| React state/context | 页面状态和当前认证用户 |
| localStorage请求记录 | 保存超时待确认操作ID，刷新后恢复 |
| Redis String | JSON目录快照、generation、限流计数 |

金额输入先按十进制字符串拆分，再生成整数分，不能用parseFloat(input)*100直接作为交易金额。数据库BIGINT上限配合业务余额上限10^12分；当前JS Number在该范围内仍可精确表示整数。若未来金额/ID超过2^53，接口应转字符串或专门大整数处理。

JWT保存在localStorage会增加XSS后的凭据风险。当前无HTML直插，Nginx模板提供CSP；生产可改HttpOnly Cookie，但需配套CSRF/SameSite策略，不能只改存储位置。

### 索引与查询

- orders(user_id,id)：WHERE user_id + ORDER BY id DESC + LIMIT。
- orders(user_id,request_id)：幂等查找和唯一约束。
- stock_ledger(blind_box_id,id)：奖池流水审计。
- wallet_ledger(user_id,id)：账户流水追溯。
- comment(player_show_id,id)：评论分页。
- FK相关索引由InnoDB维护要求，具体执行计划仍用EXPLAIN确认。
- 名称LIKE '%keyword%'普通B-tree不能高效做前缀定位，当前适用于小型目录，大量商品再评估全文搜索。
- 订单直接读快照，消除原1+2N查询；收藏用GROUP BY聚合。当前OFFSET有页码上限，深分页可改游标。

### 状态与历史

保存商品默认DRAFT；上架检查总库存与奖品合计；OFF_SALE暂停；ARCHIVED不可重新上架。采用归档，避免删除外键引用及历史奖品。version仍随库存写变化，用于诊断，当前不是CAS竞争控制。

订单当前只实现“已支付”，未实现真实待支付/发货/退款状态机。若接支付，应先区分支付订单、抽奖权益与结果，支付未确认时不能直接增加余额；退款/库存回补会改变奖池分布，需要业务约定。

## 8. 缓存、点赞与图片

目录只缓存名称、图片、系列等元数据，条目 TTL 120 秒，每次批量读取库存、售价和状态，详情/余额不缓存。创建、编辑和状态变化在提交后异步提升 generation，抽奖和补货不失效元数据。异步执行器只有一个工作线程与一个排队位置，合并重复任务；失败依赖条目 TTL，避免 Redis 延迟拖住提交回调。

元数据缺失采用固定64个锁条带，等待最多50ms，取得锁后重查缓存；同实例合并回源，不是跨实例分布式锁。Redis缓存与限流使用 Sentinel 独立资源，默认1秒内一次异常打开1秒、单请求半开探测；缺失generation以时间值初始化。缓存分页total、名称、搜索匹配和新上架条目仍可能短暂旧值，不能把缓存一致性等同于交易一致性。

点赞由数据库记录用户关系，与计数在同一事务下操作，锁晒单行后检查关系，重复点赞不增加、重复取消不减少。没有使用“Redis增量满10同步并清零”，因此避免该跨组件过程的重计/丢计风险；热点点赞仍有行锁瓶颈。

图片：限制5MB，识别实际PNG/JPEG编码、先读宽高限制尺寸和像素数，再解码重编码为PNG，丢弃原文件名和任意尾随负载，UUID命名；最多两个并发解码任务，重编码后限制10MB。仅认证用户可上传；存储目录由配置决定。重编码不是万能内容审核，当前不做涉违规内容检测；孤立上传文件尚需后续定时清理/归属管理。生产多实例用对象存储/共享目录。

## 10. 面试追问与八股补充

| 问题 | 结合项目回答 |
|---|---|
| 为什么不用固定概率？ | 有限实体池，无放回，概率必须反映实际剩余数量 |
| 为什么不用double累计概率？ | 整数数量就是权重；有界整数区间避免舍入和兜底偏差 |
| 为什么悲观锁？ | 热点池竞争高，必须串行读最新分布并扣减；CAS失败重试不必然更快 |
| 乐观锁完全无锁吗？ | 否，InnoDB UPDATE仍获取行锁；乐观指应用层版本冲突检测 |
| 什么是ACID？ | 原子性整笔回滚；一致性业务不变量；隔离性控制竞争；持久性依赖数据库配置 |
| @Transactional何时不生效？ | 自调用绕过代理、对象未被Spring管理等；项目Controller调用Service代理 |
| 默认回滚规则？ | RuntimeException/Error；本项目业务异常为RuntimeException；受检异常需另设规则 |
| 隔离级别选什么？ | 使用MySQL配置；设计不依赖普通快照读实时性，关键处用锁定读取 |
| 为什么CHECK还不够？ | 能限制非负，不能直接保证跨表总库存等于SUM(prize.stock)，需事务与对账 |
| 什么是当前读/快照读？ | 当前读锁定最新可见记录；普通一致性读可复用事务快照 |
| 死锁如何处理？ | 固定顺序、短事务、索引缩小锁范围；仍可能发生，返回可恢复错误，同ID重试 |
| 为什么Redis与MySQL不同事务？ | 两个独立资源，Spring本地数据库事务不会回滚普通Redis写 |
| Lua原子等于可回滚吗？ | 不等于；不被其他命令穿插，运行中错误不保证撤回已写命令 |
| 限流有哪些算法？ | 固定/滑动窗口、漏桶、令牌桶；当前固定窗口简单，有边界突发 |
| 缓存穿透/击穿/雪崩？ | 无效key、热点失效、集中失效；可空值缓存/单飞/随机TTL等，当前实现元数据锁条带合并加载，空值缓存/随机TTL等未全部实现 |
| 为什么缓存提交后失效？ | 元数据提交后异步失效，避免未提交时回填；条目TTL兜底失败，交易库存不靠缓存 |
| 幂等与exactly-once区别？ | 网络可重复传输，唯一约束使业务效果至多一次；成功响应可重放，不承诺网络只送一次 |
| MyBatis防SQL注入？ | 所有外部参数使用#{}预编译绑定，不用字符串拼接SQL |
| 为什么订单存快照？ | 查询不依赖当前商品名称，避免N+1并保留购买当时信息 |
| 为什么用分而不是float？ | 二进制浮点无法精确表达许多十进制金额，整数分更便于精确加减 |
| JWT无状态吗？ | token自包含签名，但当前仍查数据库角色/用户存在性，所以服务请求依赖数据库 |
| JWT如何退出？ | 当前浏览器删除token，服务端未实现jti撤销；窃取token到期前仍有效 |
| CSRF为何关闭？ | 当前Authorization Bearer由JS携带；若改自动发送Cookie，需要重新设计CSRF |
| BCrypt为什么不是加密？ | 单向带盐哈希，不可解密；密码校验用matches |
| CORS是鉴权吗？ | 否，是浏览器跨域访问策略，curl不受它保护，必须服务端授权 |
| Redis单线程就安全？ | 单命令原子，但多个命令会穿插；计数+失效需Lua |
| 索引最左前缀？ | orders(user_id,id)匹配用户过滤与排序；不能假定任意字段顺序都有效 |
| 数据库连接池越大越好？ | 否，热点锁下大池只增加等待；应匹配数据库能力和延迟预算 |
| MQ怎么引入？ | 承认异步处理中状态；outbox、至少一次投递、消费者幂等、补偿和对账 |
| 怎么证明没超卖？ | 实际并发售罄测试与SQL对账，Mock单测不足以证明 |
| 概率怎么测？ | 整数票号边界可穷举验证；抽完池组成必须精确，不能只测固定中奖比例 |
| 单体能生产吗？ | 可以，但要运维、安全、容量及故障证据；微服务不自动提高可靠性 |

## 11. 验证证据与可拓展点

离线测试验证算法、条件写失败分支、请求重放、角色权限、限流故障、实际图片编码检查和金额输入。浏览器只验了离线目录/详情的展示与响应式，不把它当交易端到端测试。

实际连接后执行接入指南的并发/故障矩阵与audit.sql。把真实结果写入验收记录，再完善部署。可拓展：批次奖池、游标分页、审计操作日志、账本导出、支付回调、订单状态机、对象存储、指标告警、热点池异步处理。每项须明确改变哪些不变量、引入什么故障状态、如何恢复。
